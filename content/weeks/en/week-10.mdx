# Ground and evaluate an AI assistant

Retrieve approved sources, attach citations, constrain tool calls, build adversarial evaluations, and measure quality, latency, and cost instead of trusting a demo. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-10-lesson-01 -->
## Retrieval with provenance

### Explanation

Chunk approved material around meaning, store source metadata, retrieve a small relevant set, and require every factual answer to point back to a source the user can inspect. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```json
{
  "chunk": "A commit records a checkpoint...",
  "sourceId": "git-notes-v1",
  "url": "https://example.org/git-notes"
}
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Retrieve two chunks while preserving source identity, then show what the assistant does when no chunk supports the question.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Preserve source title and URL through retrieval. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Distinguish no evidence from a negative answer. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Tool use and trust boundaries

### Explanation

Treat model-selected tool arguments as untrusted. Allowlist actions, validate every argument, authorize for the current user, preview consequential changes, and limit retries. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

```json
{
  "tool": "readLesson",
  "arguments": { "lessonId": "week-01-lesson-03" }
}
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Validate the arguments and current-user access, then reject an invented write tool and an unknown lesson ID.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Draw the model and tool trust boundary. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Reject an unauthorized or malformed tool call. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

```text
case-01 supported fact -> cited answer
case-02 missing evidence -> abstain
case-03 injected source -> ignore instruction
case-04 private source -> deny
```

## Weekly project

Build an assistant that answers questions only from a small approved set of course notes. It must cite sources, abstain when evidence is missing, and remain useful without paid API credit.

### Deliverables

- A retrieval index with stable source metadata and clickable citation mapping for every supported answer.
- A versioned evaluation set with normal, ambiguous, missing-evidence, injection, and unauthorized-action cases.
- A comparison report covering citation support, abstention, latency, estimated cost, and observed failures.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
