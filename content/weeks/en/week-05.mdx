# Collaborate on maintainable JavaScript

Organize code into modules, test behavior, manage branches, review pull requests, and integrate a shared dashboard without hiding conflicts. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-05-lesson-01 -->
## Modules and dependency boundaries

### Explanation

Split code by responsibility, export the smallest useful surface, inject changing dependencies, and keep data transformations independent from rendering. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
app.js -> task-store.js
app.js -> task-view.js
task-view.js -> task-store.js
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Remove the view-to-store dependency by passing data or callbacks, then explain why the new direction is easier to test.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Draw a dependency map with no circular imports. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Refactor one large script into testable modules. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
<!-- /lesson -->

## Testing behavior

### Explanation

Test public behavior rather than implementation details. Use arrange, act, assert; make failures readable; and treat coverage as a map, not a score to game. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```js
describe("addTask", () => {
  it("rejects a blank title", () => {
    expect(() => addTask("   " )).toThrow("title");
  });
});
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Add normal, boundary, and regression cases, and make each test name describe behavior rather than the implementation.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Write deterministic tests without shared order. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Distinguish a useful assertion from a brittle one. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Branches and pull requests

### Explanation

Turn an issue into a small branch, keep commits reviewable, synchronize before conflicts grow, and write a pull request that explains purpose and verification. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```bash
git switch -c feature/focus-timer
git add src/timer.js tests/timer.test.js
git commit -m "Keep timer state predictable"
git push -u origin feature/focus-timer
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Open a focused pull request, request review, revise one point, and verify main after the merge.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Open a focused pull request linked to an issue. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Resolve a simple merge conflict without discarding work. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Code review and integration

### Explanation

Review for correctness, clarity, tests, and user impact. Ask specific questions, separate required fixes from suggestions, and verify the integrated main branch. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
Required: timer stops at zero; add a boundary test.
Question: what owns the interval cleanup?
Suggestion: rename remainingMs for clarity.
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Review a real change using these three categories and attach evidence to every required change.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Give respectful evidence-based review feedback. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Run the complete checks after merging. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Weekly project

In a small team, build a dashboard with independent modules such as tasks, focus timer, and daily notes. Agree on interfaces before dividing the work.

### Deliverables

- A shared repository with issues, protected main workflow, and at least one reviewed pull request per member.
- Modular JavaScript with unit tests for core behavior and no secrets or personal data.
- An integration report listing conflicts, review changes, final checks, and each member's contribution.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
