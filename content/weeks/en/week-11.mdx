# Discover and build a capstone alpha

Find a real but safe local need, validate it with lightweight research, reduce scope, design the system, and deliver one end-to-end vertical slice. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-11-lesson-01 -->
## Problem discovery

### Explanation

Interview or observe without collecting unnecessary sensitive information. Separate what people said, what you inferred, and what remains unknown; do not start with a favorite technology. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
Evidence: three learners lose track of application deadlines.
Inference: reminders may help.
Unknown: whether they want email or a checklist.
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Rewrite a technology-first idea as a problem statement, and remove details that could identify interview participants.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Write evidence notes without identifying participants. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- State a problem without embedding a solution. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Scope and success

### Explanation

Choose one primary user and task, list explicit non-goals, define a measurable success signal, and cut features until the risky assumption can be tested in a week. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
Now: record an opportunity and deadline
Next: reminders
Later: recommendations
Not now: messaging and payments
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Cut one more feature, name the riskiest assumption, and define an observable alpha success signal.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Create a now, next, later scope. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Define success that can be observed in a pilot. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

```text
issue #1 schema + migration
issue #2 create form + server validation
issue #3 owner list + denial test
issue #4 deploy + smoke check
```

## Weekly project

Design a useful web product around a Mexican community, education, work, environment, culture, or public-service need without requiring sensitive personal or government data.

### Deliverables

- A problem brief with evidence, primary user, non-goals, success signal, risks, and privacy choices.
- An architecture map and prioritized issue backlog linked to acceptance criteria.
- A deployed vertical slice with repository history, core tests, alpha feedback, and next-iteration decisions.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
