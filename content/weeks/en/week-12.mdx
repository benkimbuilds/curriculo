# Harden, launch, and present the capstone

Finish the most valuable scope, test and observe production behavior, improve the portfolio story, and practise a concise technical interview and live demo. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-12-lesson-01 -->
## Quality and security pass

### Explanation

Test domain rules, authorization denials, keyboard flow, narrow screens, slow networks, and failure recovery. Remove secrets and unused collection before polishing minor features. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
High: another user can edit a project -> block launch
Medium: slow empty state -> fix or document
Low: icon alignment -> defer
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Triage five real findings by impact, likelihood, and recovery; resolve security and data-loss risks before polish.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Prioritize launch risks with evidence. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Close high-impact defects or document a safe limitation. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
<!-- /lesson -->

The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying.
```text
commit abc123 -> build -> migration 004 -> deploy
health 200 -> owner flow pass -> denial pass
backup created -> rollback rehearsed
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.

- Run and record a recovery drill. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Demo and interview practice

### Explanation

Plan a reliable three-minute story, prepare fallback screenshots, answer with situation-action-result evidence, and admit uncertainty while explaining how you would investigate. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
0:00 problem and user
0:30 primary journey
2:00 engineering decision
2:35 evidence and learning
2:55 close
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Practise once live and once with fallback captures, then answer one tradeoff and one unknown with evidence.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Deliver a timed live demo with a fallback. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Explain code decisions without reading the code aloud. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Weekly project

Ship the capstone's primary journey at a stable HTTPS URL, present it to peers, and publish a portfolio case study. A team is optional, but individual contributions must be explicit.

### Deliverables

- A production release with tested primary flow, authorization, validation, responsive and keyboard checks, monitoring, and rollback notes.
- A reproducible repository with tests, architecture, privacy and AI disclosures where relevant, exact deployed commit, and personal contribution record.
- A concise case study, three-minute demo, feedback log, retrospective, and prioritized next steps based on evidence.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
