# Harden, launch, and present the capstone

Finish the most valuable scope, test and observe production behavior, improve the portfolio story, and practise a concise technical interview and live demo. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-12-lesson-01 -->
## Quality and security pass

### Explanation

A quality pass starts with the promises in your acceptance criteria. Test the rules whose failure would lose work, expose data, or mislead a user before polishing minor decoration. For the loan project, that means availability, ownership, persistence, and recovery. A screenshot alone cannot prove these.

Use different levels of tests for different questions. A unit test checks a small domain rule without a browser or database. An integration test checks real boundaries such as a database constraint or authenticated server operation. A browser test checks the user journey, labels, focus, and rendered result. Repeating the same assertion at every level adds little; place each check where its failure can be understood.

Authorization tests need at least two accounts. Verify that account A can access A's record and account B cannot, including by changing a URL or request body directly. Hiding links is not enough. Test expired sessions, malformed ids, missing records, and repeated submissions. Use synthetic data and disposable environments.

Inspect the interface with keyboard navigation, narrow width, enlarged text, and slow networking. Labels should explain controls, errors should identify recovery, and focus should stay meaningful after changes. Browser overflow measurements do not catch text pressed against dividers or unreadable hierarchy; inspect the actual screens too.

### Example

This Node unit test describes a small domain rule. Keep a separate integration test for the database's one-active-loan invariant, because two concurrent requests can both pass this pure function before either inserts a record.

~~~js
import test from "node:test";
import assert from "node:assert/strict";

function canBorrow({ active, disabled }) {
  return !active && !disabled;
}
test("only available enabled items can be borrowed", () => {
  assert.equal(canBorrow({ active: false, disabled: false }), true);
  assert.equal(canBorrow({ active: true, disabled: false }), false);
  assert.equal(canBorrow({ active: false, disabled: true }), false);
  assert.equal(canBorrow({ active: true, disabled: true }), false);
});
~~~

The truth table explains all combinations. It does not replace input validation: your boundary should reject missing or incorrectly typed fields rather than relying on truthiness. It also does not prove server ownership checks, which require separate tests against the real operation.

### Guided exercise

1. Map each acceptance criterion to one useful automated or manual check. Identify gaps before adding more tests.
2. Run the domain checks and deliberately break one rule to confirm the test detects it.
3. Exercise own-versus-other account reads and writes through the server, not only the interface.
4. Inspect all pages used by the main journey at phone and desktop widths, by keyboard, and with slow network settings.
5. Review repository history, logs, forms, and configuration for secrets and unnecessary personal-data collection. Remove unused collection and document any remaining issue.

### Checkpoint

- A report connects each important promise with a passing check or an explicit unresolved defect.
- Another account cannot read or mutate private records by altering requests.
- The main journey remains readable and recoverable under narrow screens, keyboard input, and network failure.

## Production readiness

### Explanation

Production readiness means the deployed system can start, serve its real dependencies, and recover from expected failures. A successful build is necessary but does not prove database connectivity, email delivery, worker execution, or the user's complete journey.

Separate liveness from readiness. Liveness says the process responds; readiness says required dependencies are usable. In this platform, /api/health and /api/ready serve those different purposes. A worker needs its own evidence: a running process plus a completed synthetic job or an appropriate queue check, not merely the web page loading.

Configuration belongs to the environment that uses it. Database URLs, auth secrets, and email credentials stay server-side. The public origin and trusted origins must match the actual HTTPS site. A successful local email captured by a development inbox does not prove production delivery. Verify registration, verification, and recovery with authorized test accounts if those are part of your project.

Migrations change persistent data and need a recovery plan. Prefer changes compatible with both old and new application versions when rolling deployments. Back up before risky changes and practice restoring into a separate database. Having a backup listed in a dashboard is weaker evidence than a restore you have tested.

Application rollback does not automatically reverse schema changes or restore lost data. Record the prior version, deployment steps, and conditions for rollback. Avoid destructive migration edits just to make an old application start.

### Example

For this repository, the release checklist can use these existing commands. Run database operations only against the intended environment; inspect its identity before executing.

~~~sh
pnpm lint
pnpm typecheck
pnpm test
pnpm content:validate
pnpm build
~~~

After deployment, replace the example origin with your real site:

~~~sh
curl --fail --silent --show-error https://your-app.example/api/health
curl --fail --silent --show-error https://your-app.example/api/ready
~~~

A 200 response is only one check. Confirm the deployed commit, inspect safe logs for startup and migration errors, and perform a synthetic user journey that writes and reads data. If your project includes email and a worker, verify them explicitly. Do not paste credentials into screenshots or reports.

### Guided exercise

1. Create an environment checklist naming each required variable and owning service, with no secret values.
2. Apply migrations to a fresh disposable database and start the application from documented commands.
3. Deploy, check health/readiness, and run the main journey from a clean test account.
4. Create and restore a test backup into another disposable database; compare expected record counts and constraints.
5. Rehearse returning to a prior compatible application version. Record what requires a separate database recovery decision.

### Checkpoint

- Your report distinguishes build success, healthy process, usable database, email delivery, and worker execution.
- The deployed version and successful synthetic journey are recorded.
- Backup and rollback instructions are reproducible and do not assume code rollback reverses data changes.

## Portfolio and documentation

### Explanation

A portfolio reviewer may have only a few minutes. Help them understand the problem, your contribution, and the evidence that the project works. A list of technology logos says little about engineering judgment. Explain why you chose a design, what alternatives you considered, and what limitation remains.

Write the README for a person who has never seen the project. Begin with the user's problem and the main result, then provide a screenshot or short demo link. State whether it is a learning project, an adaptation, or work used by real people. Do not invent adoption numbers or claim a team feature was solely yours.

Separate quick evaluation from local setup. A nontechnical reviewer needs a readable description and demonstration. A technical reviewer needs prerequisites, exact commands, environment-variable names, migrations, seed data, and tests. Use placeholders for secrets and explain how to obtain local values. Keep setup instructions synchronized with the actual package scripts.

Documentation should expose limitations rather than hide them. If AI uses a deterministic stub, label it. If email requires configuration, say so before the reviewer tries account recovery. If automated evaluation only covers some criteria, distinguish it from human assessment. Honesty lets someone evaluate the project fairly.

### Example

Use this outline and fill it with project-specific facts, not generic adjectives:

~~~markdown
# Equipment borrowing
A small application for checking shared equipment availability and recording loans.

## Demo
Public URL, screenshot, and safe instructions for trying a synthetic example.

## What I built
My routes, domain rules, tests, and collaboration responsibilities.

## Architecture
Browser -> authenticated server operation -> PostgreSQL constraints.

## Run locally
Required runtime version, install command, environment template,
migration and seed commands, then start command.

## Verify
Test commands and the main manual journey.

## Decisions and limits
Why one active loan is enforced in the database.
What is outside scope, and what remains unverified.

## Credits
Source curriculum, libraries, adapted material, and applicable licenses.
~~~

For a case study, show one decision in depth: two borrowers submitted at once; the application needed a database constraint; the second request now receives a recoverable conflict. Include a test or trace. That explains your work more clearly than saying “robust backend.”

### Guided exercise

1. Select two or three projects that demonstrate different skills. Remove broken links and redundant examples.
2. Write a concise case study with problem, constraints, contribution, decision, evidence, and next improvement.
3. Follow your README from a clean clone using only its instructions. Record and fix every missing step.
4. Ask a nontechnical peer to explain the project after one minute and a technical peer to run one test.
5. Review screenshots, sample accounts, and git history for private information. Attribute adapted work and collaborators.

### Checkpoint

- A reviewer identifies the problem and your personal contribution quickly.
- Setup and verification succeed without undocumented manual actions.
- Claims about AI, deployment, usage, and evaluation match the evidence rather than marketing language.

## Demo and interview practice

### Explanation

A demonstration is a short explanation supported by a reliable user journey. Choose one problem and show its resolution. A three-minute demo does not need to visit every page. Too many features make it harder for a reviewer to understand the core behavior and your decisions.

Plan the starting state. Use synthetic data, a test account, and a known item available to borrow. Verify the deployed version before presenting. Prepare screenshots or a short recording in case the network fails, and label them as recorded evidence rather than pretending they are live.

Use a simple structure: context, action, result, and one technical decision. In the loan project, explain the wasted-trip problem, show current availability and checkout, then show the persisted loan after refresh. Briefly describe how the database prevents simultaneous duplicate loans. End with a limitation and the next improvement you would test.

Interview answers should also connect claims to evidence. A situation-action-result structure keeps the explanation concrete. Distinguish your contribution from the team's. Explain an unsuccessful attempt if it reveals what you learned, but spend most time on the final reasoning and proof.

### Example

A three-minute outline could be:

~~~text
0:00–0:30  Who borrows equipment, and what went wrong before.
0:30–1:20  Sign in with a test account, choose an item, and borrow it.
1:20–1:45  Refresh and show the persisted loan.
1:45–2:20  Explain the concurrency test and unique active-loan constraint.
2:20–2:45  Show one failure recovery and one limitation.
2:45–3:00  State the next experiment and invite questions.
~~~

For a technical interview problem, start by restating inputs and expected outputs, asking about constraints, and working through a small example. A straightforward correct solution is a good starting point. Explain complexity and improvements afterward. If you do not know a method, say what you would inspect in documentation instead of fabricating a name.

Prepare for questions such as “What would break with two simultaneous users?”, “How do you prevent another account reading this record?”, and “What did the test fail to cover?”. Answers should point to actual code and evidence. Admitting a known limitation with a plan is stronger than claiming complete reliability.

### Guided exercise

1. Write and rehearse a three-minute script using one real end-to-end journey.
2. Run it from the documented starting state twice, including a fresh browser session.
3. Practice a network failure and switch to clearly labelled screenshots without losing the explanation.
4. Pair with a peer for five technical questions and a small coding problem. Think aloud, clarify, test, and summarize.
5. Record feedback on clarity, timing, unsupported claims, and unanswered questions. Revise and rehearse once more.

### Checkpoint

- The live demo fits three minutes and proves persistence and the main rule.
- A fallback is available and honestly identified if needed.
- You can explain one tradeoff, one defect you repaired, and one remaining limitation with concrete evidence.

## Weekly project

Ship the capstone's primary journey at a stable HTTPS URL, present it to peers, and publish a portfolio case study. A team is optional, but individual contributions must be explicit.

### Deliverables

- A production release with tested primary flow, authorization, validation, responsive and keyboard checks, monitoring, and rollback notes.
- A reproducible repository with tests, architecture, privacy and AI disclosures where relevant, exact deployed commit, and personal contribution record.
- A concise case study, three-minute demo, feedback log, retrospective, and prioritized next steps based on evidence.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
