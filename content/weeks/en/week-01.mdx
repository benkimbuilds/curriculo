# Start as a developer

Set up a dependable workspace, learn the terminal without fear, publish with Git, and build a semantic personal profile from scratch. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

## Your computer and the web

### Explanation

A page in your browser may come from a file on your computer or from a remote server. Distinguish those situations before installing tools. The editor changes files, the terminal runs commands, the browser interprets HTML and executes JavaScript, and the server answers requests. Git records versions; GitHub hosts repositories. These tools cooperate but do not automatically replace one another.

When you enter an HTTPS address, the browser needs to locate the server. DNS associates a domain with an address. Requests and responses travel over networks in packets. After receiving HTML, the browser may request CSS, images and JavaScript. A search engine is a website that helps locate other sites; it is not the browser or the whole internet.

On Windows you can begin HTML exercises with native VS Code and Chrome. For Unix command exercises use the Ubuntu WSL2 environment prepared by the lab. Confirm that the terminal is Ubuntu before copying Bash commands, store repositories in the Linux home directory, and open VS Code connected to that environment. On macOS use Terminal and VS Code directly. Understanding the concepts does not require replacing your operating system.

Choose a project directory you can find without relying on a recent-files menu. Give each project its own folder and open the whole folder in VS Code. Avoid leaving related files scattered through Downloads and moving them without checking paths. A file named index.html.txt is not the same filename as index.html, even if your file manager hides extensions.

Saving only updates the file on disk. Refreshing asks the browser to read it again. Pushing to GitHub sends code, while publishing a website additionally requires a service that serves it. These actions can happen at different times. If a page looks outdated, first check which copy you opened, whether you saved, and whether deployment finished.

### Example

Create this file inside a new profile-practice folder:

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <title>My practice environment</title>
  </head>
  <body>
    <h1>I am building my first page</h1>
    <p>This file lives on my computer.</p>
  </body>
</html>
```

Open it in Chrome and inspect the address. A file address means you are reading a local file, not a public deployment. Change the tab title and visible heading separately, saving before refreshing. Disconnecting from the internet does not stop the browser from reading this local file, though external images or styles would still need a connection.

### Guided exercise

1. Draw the browser, editor, terminal, project folder, GitHub and server. Connect them and label what information moves along each connection.
2. Create, save and open the file. Record its location privately; do not publish personal details embedded in your username or directory names.
3. Close both applications and find the same project again through the file manager. Open the whole folder instead of making a second copy.
4. Change one sentence, observe before saving, then save and refresh. Explain each state.
5. Compare your file with an HTTPS website and identify which activities need a network connection.

### Checkpoint

- Explain what each tool does using your own file as evidence.
- Close and reopen the same project and distinguish its local copy from a published website.
- Explain why saving, committing and deploying are different operations.

## Terminal fundamentals

### Explanation

The terminal accepts written instructions and the shell interprets their syntax. Each session has a working directory. Many commands resolve paths from that directory, so knowing where you are comes before creating, moving or deleting anything. Do not type the prompt symbol shown in a tutorial: a dollar or percent sign usually indicates that the shell is ready.

An absolute path describes a location from the filesystem root. A relative path starts at the current directory. A dot represents that directory and two dots represent its parent. A folder becomes a useful project location because of how you organize files, not because its name has special powers.

In PowerShell, Get-Location shows your location, Get-ChildItem lists contents, and Set-Location changes directories. New-Item creates a file or directory according to ItemType. On macOS or Ubuntu in WSL the corresponding tools include pwd, ls, cd, touch and mkdir. Similar aliases do not mean every command or option is interchangeable.

A path error rarely requires reinstalling software. Read the message, check the current directory and spelling, and use Tab completion. Linux paths distinguish uppercase and lowercase. Put a path containing spaces in quotes so the shell treats it as one argument.

Use the command history to revisit a previous instruction, but read it before executing again. A command that was appropriate in one directory may target different files after navigation. Repetition saves typing only when its context still matches your intention.

Deletion commands may bypass the trash. Practice only inside the directory created for this exercise and inspect its contents first. Do not run recursive deletion against your home folder or a repository containing work. A powerful command is not automatically the appropriate response to uncertainty.

### Example

In native Windows PowerShell:

```powershell
Get-Location
New-Item -ItemType Directory terminal-practice
Set-Location terminal-practice
New-Item -ItemType File notes.txt
Get-ChildItem
```

On macOS or Ubuntu in WSL:

```bash
pwd
mkdir terminal-practice
cd terminal-practice
touch notes.txt
ls
```

Both sequences create a directory, enter it and create an empty file. Do not run both against the same location without checking what already exists. Open notes.txt in the editor, add a sentence and save. The terminal and editor see the same file only when their environment and path agree.

### Guided exercise

1. Choose the appropriate shell and record the starting location. Create the practice directory and verify that it exists before entering it.
2. Create notes.txt, edit and save it, then list the directory again. Open the file to verify the sentence exists on disk.
3. Create a subdirectory and enter it. Show the current location, return to the parent and explain which part of the path changed.
4. Rename only the practice file using Rename-Item in PowerShell or mv in Bash. Verify that its contents remain intact.
5. Read the help for a command you intend to use. Before removing the practice material, inspect the exact path and contents, delete only the practice file, then remove the empty directory.

### Checkpoint

- Navigate to a directory and back while explaining each path instead of guessing.
- Identify which commands belong to PowerShell and which belong to Bash.
- Show what evidence you would inspect before deletion and explain how you recognize a command whose scope is too broad.

## Git and GitHub

### Explanation

Git records project versions on your computer. GitHub hosts a remote copy and supports collaboration. You can save a file without committing it, commit without publishing, and publish source code without deploying a website. These states matter because each operation preserves or shares a different kind of progress.

The working tree contains files you edit. The staging area contains exactly the changes selected for the next commit. The repository stores commits and their relationships. git add stages a particular version: editing again afterward does not silently update that selection. git status helps distinguish untracked, modified and staged work.

A commit should express one understandable intention, such as adding navigation or fixing a broken link. Combining unrelated work makes review and reversal harder. Its message explains purpose instead of merely saying updated. That history also helps when you return after several days and no longer remember why a line was written.

Read the actual diff instead of relying only on filenames. A file may contain several unrelated edits, and a generated or downloaded file may include information you did not intend to publish. Reviewing the staged content connects your commit message to evidence of what is being recorded.

A remote has a name, usually origin, and a URL. main is a branch rather than a server. git push origin main sends that branch's commits to the configured remote. git pull obtains and integrates remote work; do not treat it as a magic repair command when you have pending changes or a conflict. Read the state and understand which versions differ first.

Configure identity and authentication through the preparation lessons. On a shared computer, do not leave private keys, logged-in sessions or someone else's global identity behind. Use GitHub's private email address if you do not want your personal address published. Never stage passwords or secret files, even if you intend to delete them later: repository history can retain them.

### Example

Inside a practice repository containing index.html:

```bash
git status
git diff
git add index.html
git diff --staged
git commit -m "Explain the profile goal"
git log --oneline
git remote -v
git push origin main
```

Before committing, compare the staged diff with the message. After pushing, open GitHub and verify the same commit. A clean working tree means no pending local file changes; it does not prove that all commits have reached the remote.

### Guided exercise

1. Create a practice repository with a README on GitHub and clone it using your configured authentication. Open that folder and verify origin.
2. Make two small, different changes to README and index.html. Run status and describe both.
3. Stage only index.html and use the staged diff to prove what will enter the commit. Commit it while leaving the README change pending.
4. Stage and commit the README separately. Review both messages and push.
5. Open the repository in the browser and compare files and commit identifiers with your local history. Document how to open the page, what you built and what you checked.

### Checkpoint

- Demonstrate pending, staged, committed and published states with the two files.
- Explain origin and main and show how you know the newest commit reached GitHub.
- Show two focused commits and explain why their separation makes the project easier to review.

## Semantic HTML

### Explanation

HTML communicates what content means. A heading identifies a topic, a list groups entries, a link navigates to a resource, and a button performs an action. Choosing elements solely for their default appearance creates confusing structure. CSS can resize a heading without replacing it with a large paragraph.

A document begins with a doctype and an html element declaring its language. head contains metadata such as encoding and tab title. body contains visible page content. Within it, header introduces a site or section, nav groups significant navigation, main contains the central content, and footer closes with related information. A section usually needs a heading describing its subject; it is not merely a styling box.

Headings form a hierarchy. Use one h1 for this page's overall subject, h2 for sections and h3 when a section truly has subsections. Do not skip levels to obtain smaller type. Reading only the headings should reveal a coherent outline of the page.

Links need an href destination and text that lets people anticipate it. An informative image needs alternative text conveying its relevant information; a purely decorative image can use an empty alt. Lists use ul or ol depending on whether sequence matters, and li for each entry. If you add a form, associate each label with its control through for and id. A disappearing placeholder is not a replacement for a persistent label.

Indentation displays relationships, but tags create the actual tree. Close the innermost element before its parent and resolve paths from the document that uses them. Browsers attempt to repair invalid markup, so a page that appears reasonable may still contain structural errors.

Think about the reading order before arranging anything visually. Someone following the document linearly should encounter the introduction, relevant navigation and project information in a useful sequence. Changing font size or moving boxes later will not repair an outline whose meaning is unclear. Write the content first and choose elements that express its relationships.

### Example

```html
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Ana · Developer profile</title>
  </head>
  <body>
    <header>
      <h1>Ana learns web development</h1>
      <nav aria-label="Main">
        <a href="#projects">Projects</a>
      </nav>
    </header>
    <main>
      <section id="projects">
        <h2>Projects</h2>
        <ul><li>My first recipe website</li></ul>
      </section>
    </main>
    <footer><p>A place to share what I learn.</p></footer>
  </body>
</html>
```

The link targets the projects ID on the same page. The tab title and h1 serve different purposes. The content still has a useful structure without CSS. Do not publish your phone number, exact address or other personal details just to fill a profile.

### Guided exercise

1. Write a plain-text outline covering introduction, learning goal, projects and a GitHub link. Choose appropriate regions and headings.
2. Build a complete document using your own content. Include a project list and navigation pointing to a real section.
3. Move through links with Tab and activate them with Enter. Verify that their destination matches their text.
4. Validate with the W3C HTML validator. Fix the first error, validate again and document the outcome.
5. Disable any styles you added and ask another person to explain the outline. Adjust the structure if the reading order is unclear.

### Checkpoint

- Justify tags by function, including the distinction between links and buttons.
- Show a coherent heading hierarchy and validation evidence with no unresolved errors.
- Verify keyboard navigation and explain what remains understandable without styling.

Create and publish a one-page profile that introduces your learning goal, shows a small project list, and gives visitors a clear way to reach your GitHub profile.

- A public GitHub repository with at least five purposeful commits.
- A deployed HTTPS page containing semantic header, navigation, main, sections, and footer.
