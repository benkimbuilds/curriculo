# Start as a developer

Set up a dependable workspace, learn the terminal without fear, publish with Git, and build a semantic personal profile from scratch. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-01-lesson-01 -->
## Your workstation and the web

### Explanation

Map the browser, editor, terminal, files, and remote services before installing tools. Follow the Windows PowerShell path or the matching macOS Terminal path and learn where projects belong. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
Browser <- index.html <- VS Code
             ^
        project folder
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Add GitHub and the deployed site to the map, then mark which arrows need a network connection.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Explain what each development tool does. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Create and reopen a project folder safely. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
<!-- /lesson -->

```powershell
Get-Location
New-Item -ItemType Directory practica

Get-ChildItem
```

## Git and GitHub

### Explanation

Use status, add, commit, log, remote, push, and pull in a small repository. A commit is a clear checkpoint with a reason, not a backup of random files. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```bash
git status
git add index.html
git commit -m "Explain the profile goal"
git log --oneline
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Change a second file, stage only one file, and use status to prove what will and will not enter the commit.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Describe the working tree, staging area, and repository. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Publish a sequence of focused commits. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Semantic HTML

### Explanation

Turn a content outline into headings, landmarks, links, lists, images, and forms whose structure still makes sense without visual styling. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```html
<header>
  <h1>Ana learns the web</h1>
</header>
<main>
  <section><h2>Projects</h2></section>
</main>
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Add navigation and a footer while keeping one h1 and a heading order that never skips a level.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Choose elements for meaning instead of appearance. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Validate HTML and repair reported errors. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Weekly project

Create and publish a one-page profile that introduces your learning goal, shows a small project list, and gives visitors a clear way to reach your GitHub profile.

### Deliverables

- A public GitHub repository with at least five purposeful commits.
- A deployed HTTPS page containing semantic header, navigation, main, sections, and footer.
- A README with setup, validation evidence, and one learning reflection.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
