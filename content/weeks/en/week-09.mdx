# Add a bounded AI feature

Frame a narrow model-assisted task, protect private data, require structured output, control cost, and keep the product useful when the model is unavailable. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-09-lesson-01 -->
## AI product framing

### Explanation

Separate the user problem from the model. Define an input, allowed output, success examples, unacceptable behavior, and a no-cost workflow before choosing a provider. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```json
{
  "input": "Plan a community workshop",
  "output": ["Choose a date", "List materials"]
}
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Create the same result with a deterministic template and state the specific user benefit a model would need to add.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Write a bounded task contract. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Explain when ordinary code is the better solution. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Prompts and structured output

### Explanation

Provide necessary context, delimit untrusted input, request a small schema, and parse the response as unknown. Reject extra or missing fields instead of hoping prose stays stable. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```ts
const suggestionSchema = z.object({
  title: z.string().min(1).max(80),
  rationale: z.string().max(200),
  effort: z.enum(["small", "medium"])
});
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Parse missing, extra, wrong-type, and oversized responses as unknown and reject invalid output before display.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Create and validate an output schema. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Keep instructions separate from user content. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

## Privacy, safety, and cost

### Explanation

Minimize what leaves the server, never send secrets, state retention assumptions, rate-limit requests, cap tokens, use timeouts, and record cost without logging sensitive prompts. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```text
Browser -> App server -> AI provider
             limits: 5/min, 800 tokens, 8 s
             logs: status + cost, no learner text
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Remove every unnecessary field from the flow and show where secrets, rate limits, timeout, and cost caps are enforced.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

## Fallbacks and user control

### Explanation

Let the person review and edit suggestions. Preserve their original work, label model output, handle refusal and malformed results, and provide a useful deterministic alternative. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

```ts
try { return await suggest(input); }
catch { return templateSteps(input); }
```

## Weekly project

Add one optional feature to the tracker that suggests small next steps from a non-sensitive project description. The user must approve every suggested task before saving.

### Deliverables

- A documented task contract, structured-output schema, and validation before persistence.
- Rate limit, timeout, cost cap, generic safe errors, and logs that exclude descriptions and credentials.
- An editable review step and a no-cost template fallback that keeps the workflow usable.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
