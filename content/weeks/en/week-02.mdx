# Design responsive, inclusive pages

Use CSS deliberately, make layouts adapt from phones to lab monitors, and check that keyboard and screen-reader users can understand the result. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-02-lesson-01 -->
## CSS foundations

### Explanation

A stylesheet does not execute from top to bottom like a sequence of JavaScript instructions. The browser collects declarations that apply to an element and resolves conflicts through the cascade. Within ordinary author rules in the same layer, selector specificity helps determine which declaration wins; when that is equal, the later declaration wins. Inheritance is a different mechanism: some properties, including text color, can pass from a parent when the child does not have its own winning declaration.

Consider a paragraph with class `notice` inside `main`. The selector `.notice` matches it, and so does `main .notice`. The second selector has an additional type component, so its normal color declaration wins over either of the simple class rules below. Moving a less specific rule to the bottom does not automatically beat a more specific one. Avoid adding `!important` as your first response: inspect why the existing declaration wins and make the intended relationship clear.

Spacing has a separate model. Every box has content, padding, border, and margin. Padding separates content from its border; margin separates the box from neighboring boxes. With the default content-box sizing, a declared width excludes padding and borders. With border-box sizing, they are included. A title touching a card border usually needs interior padding, not extra margin between neighboring cards.

Use relative units deliberately. A rem follows the root font size, while an em can follow the element's font size. A thin border may intentionally use pixels. There is no single unit that solves every layout. Ask what should grow when the text grows, then choose the unit that expresses that relationship. Keep browser font preferences and zoom in mind when testing.

### Example

```css
*, *::before, *::after { box-sizing: border-box; }
.notice { color: navy; }
main .notice { color: teal; }
.notice { color: purple; }
.card {
  max-width: 36rem;
  padding: 1.5rem;
  border: 1px solid #667788;
  margin-block: 1rem;
}
.card p { line-height: 1.5; }
```

Create a paragraph inside a card inside main. Open DevTools, select the paragraph, and inspect both Styles and Computed. Crossed-out declarations show losing rules; the computed color shows the result. Then inspect the card's box diagram. Compare its content edge, padding edge, and border rather than guessing which number controls the visible space.

### Guided exercise

1. Create an HTML page with a main element, two cards, headings, paragraphs, and a link. Connect an external stylesheet and verify its request succeeds.
2. Apply the example and predict the paragraph color before opening Computed. Disable the winning rule and explain the next winner.
3. Remove the card padding, observe the crowded border, and restore it. Change the margin separately and explain why it affects a different relationship.
4. Add a long heading and increase the browser's default text size. Replace any fixed height that clips content with natural height or a justified minimum.
5. Read [MDN's cascade guide](https://developer.mozilla.org/en-US/docs/Learn/CSS/Building_blocks/Cascade_and_inheritance) and [box model guide](https://developer.mozilla.org/en-US/docs/Learn/CSS/Building_blocks/The_box_model). Record one inspected rule and one measured spacing correction.

### Checkpoint

- Explain why teal wins in the example and show the competing declarations in DevTools.
- Identify the content, padding, border, and margin of your card, and demonstrate which change fixes text touching its border.
- Show that longer text remains visible when the font size increases.

## Layout systems

### Explanation

Start with normal document flow. Headings and paragraphs already stack vertically, and text wraps into available space. You do not need a positioning system for every element. Introduce Flexbox when a group needs coordinated behavior along one main axis, and Grid when rows and columns need a shared structure.

A row of actions is a useful Flexbox case. Each button has content with a natural size; the group can align items, maintain gaps, and wrap when the combined widths no longer fit. The main axis depends on flex-direction. Justify-content distributes along that axis, while align-items controls the cross axis. If you change direction, do not assume the same property still means horizontal alignment.

A project gallery is a useful Grid case. The container defines column tracks, and its direct children occupy cells. Repeat with auto-fit and minmax can determine how many readable columns fit without naming a particular phone or tablet. A one-fr maximum distributes remaining space across columns. The minimum needs to fit inside the container too: an unconditional 16rem minimum can overflow a narrower embedded panel.

Grid and Flexbox work together. A card can be a Grid item in the gallery while its action row is a Flex container. These relationships exist at different levels. Adding display flex to the card does not change the parent gallery's column definition. Identify the responsible parent before editing a layout rule.

Content introduces constraints. A long URL, a large image, or an unbreakable label can create a minimum size that resists shrinking. Inspect the offending child rather than hiding overflow on the whole page. Use min-width zero where a flexible child needs permission to shrink, and give long text an appropriate wrapping policy. Keep reading order in HTML logical even if Grid could visually move an item elsewhere.

### Example

```css
.cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 16rem), 1fr));
  gap: 1.5rem;
}
.card { min-width: 0; padding: 1.5rem; border: 1px solid #9aa7b0; }
.card h2 { overflow-wrap: anywhere; }
.actions { display: flex; flex-wrap: wrap; gap: .75rem; align-items: center; }
.actions a { padding: .75rem 1rem; }
```

The gallery gap separates cards, while card padding separates text from borders. The action gap separates controls. Those values serve different purposes. A larger gallery gap cannot repair text crowded inside a card. Activate the Grid overlay to see tracks and use the box model inspector to see padding.

### Guided exercise

1. Build a gallery with six cards, each containing a title, description, and two real links. Keep the markup in the intended reading order.
2. Apply the example and inspect the column tracks. Resize the parent until a column disappears, then explain the minimum and gaps that caused the change.
3. Replace one title with a long URL and one description with several paragraphs. Confirm every card can grow vertically without clipping.
4. Add a third action with a long label. Observe how Flexbox wraps the actions independently from the Grid columns.
5. Compare [Grid layout](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_grid_layout) with [Flexbox basics](https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_flexible_box_layout/Basic_concepts_of_flexbox). Write one reason for each system used in your page.

### Checkpoint

- Identify which container controls the gallery and which controls the buttons inside each card.
- Demonstrate an added card and a long title without changing device-specific CSS.
- Explain why gap, padding, and a fixed height are not interchangeable layout fixes.

## Responsive design

### Explanation

Responsive implementation means preserving a usable interface as the available space changes. A page can pass at one phone width and one desktop width while failing between them. Test a continuous range and vary content as well as screen size. Zoom and larger text also change how much room the interface effectively has.

Begin with a narrow layout that works in normal flow. Let content containers grow up to a readable maximum, then center them rather than stretching paragraphs across an ultrawide screen. Give images a flexible maximum width and automatic height to preserve their ratio. If an image must fill a fixed visual frame, use object-fit deliberately and verify that the crop preserves its subject.

A media query applies declarations when the viewport satisfies a condition. It does not add specificity or override the cascade automatically. Choose a breakpoint when the actual content needs another arrangement, not because a device list says tablets begin at a particular number. A sidebar can move above the article when there is insufficient room for both. A small action row may simply wrap and need no query.

The viewport meta tag tells a mobile browser to use the device's available CSS width instead of shrinking an artificial desktop-sized viewport. It sets an initial scale; it should not prevent the user from zooming. Frameworks may emit it for you, so inspect the rendered document before adding duplicates.

Forms expose responsive defects quickly. A label may wrap, an error may be several lines long, and a virtual keyboard may reduce the visible area. Keep labels above fields when that avoids squeezed columns, allow controls to fill their container, and avoid fixed heights on error messages. Do not remove instructions on small screens just to make a screenshot fit.

### Example

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

```css
.page { width: min(100% - 2rem, 70rem); margin-inline: auto; }
img { max-width: 100%; height: auto; }
.content { display: grid; gap: 2rem; }
input, textarea, select { max-width: 100%; font: inherit; }
@media (min-width: 52rem) {
  .content { grid-template-columns: minmax(0, 2fr) minmax(14rem, 1fr); }
}
```

Below the breakpoint, the content regions stack in source order. Above it, they form a main column and a secondary column. The minimum sidebar width is a conscious constraint; verify that the remaining main width is still sufficient at the exact moment this layout activates.

### Guided exercise

1. Use your gallery and add an introduction, a large image, and a small information-request form with visible labels.
2. Test at 320, 360, 768, and 1280 CSS pixels. Then drag slowly between those widths and note the first point where content becomes cramped.
3. Add a media query only for a necessary structural change. Test just below, exactly at, and just above the breakpoint.
4. Zoom to 200%, paste a long email-shaped sample into the field, and display a multi-line error. Ensure no content disappears behind fixed boxes.
5. Inspect the largest offending element if horizontal scrolling appears. Fix its width, minimum, or wrapping rule instead of masking the document with overflow hidden.
6. Follow [MDN's responsive design introduction](https://developer.mozilla.org/en-US/docs/Learn/CSS/CSS_layout/Responsive_Design) and [Chrome device mode](https://developer.chrome.com/docs/devtools/device-mode/). Record screenshots and the content condition that justified your breakpoint.

### Checkpoint

- Show the same content at narrow, intermediate, and wide widths without lost information.
- Explain why your breakpoint exists and show behavior immediately around it.
- Demonstrate that images retain their proportions and the form remains usable with enlarged text.

## Practical accessibility

### Explanation

Accessibility is part of whether someone can complete the task. For this week's page, focus on a concrete journey: find the service, understand its conditions, enter a request, and recognize the result or error. A page that looks polished but cannot be operated by keyboard has not completed that journey for everyone.

Use semantic HTML before adding ARIA. A button performs an action; a link with an href navigates. A div styled to resemble a button does not automatically receive focus, respond to Enter or Space, or announce its role. Headings describe the hierarchy, and main and nav identify important regions. Choose heading levels for structure and change their appearance with CSS.

Every input needs a meaningful label. The label's for value should match a unique input id. The name attribute serves a different purpose: it identifies the submitted value. Use email for an email address, tel for a telephone, and text for identifiers that are not quantities. A placeholder is only a disappearing hint and cannot replace a persistent label.

Explain constraints before submission. Required, minlength, and type-based checks can provide a useful first layer, but browser checks are not server protection. A demonstration form should not pretend to create a real account. When an error appears, identify the affected field and how to fix it while preserving what the person entered. Associate additional instructions through aria-describedby when appropriate.

Keyboard users need visible focus and a sensible order. Tab and Shift+Tab should follow the document logically; Enter and Space should activate native controls as expected. Closed panels must not contain invisible focus stops. Preserve the browser's focus indicator or replace it with a clear one, and check that borders or overflow do not clip it.

Color and images also communicate information. Check foreground/background contrast, keep links distinguishable by more than color, and write alternative text according to an image's purpose. Decorative images can have an empty alt. If you add motion, provide a reduced-motion alternative that keeps the information available.

### Example

```html
<form action="/request" method="post">
  <label for="email">Email (required)</label>
  <p id="email-help">We will use this address to reply about the workshop.</p>
  <input id="email" name="email" type="email" required
         autocomplete="email" aria-describedby="email-help">
  <button type="submit">Request workshop information</button>
</form>
```

```css
:focus-visible { outline: 3px solid #155b9e; outline-offset: 3px; }
label, input { display: block; }
input { width: 100%; padding: .75rem; margin-block: .5rem 1rem; }
```

The route is illustrative: connect a real handler or clearly label the page as a demonstration. Inspect the field's accessible name and description, then click the label to verify focus moves to the input.

### Guided exercise

1. Complete the whole page using only Tab, Shift+Tab, Enter, and Space. Record the first missing or confusing focus stop.
2. Inspect heading order and replace interactive generic containers with appropriate native elements.
3. Test empty and invalid input, then correct it. Verify helpful feedback and preservation of other values.
4. Check text and link colors with [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/) and review image alternatives using [WebAIM's alt-text guide](https://webaim.org/techniques/alttext).
5. Run a browser accessibility audit, fix relevant findings, and repeat the manual journey. If available, test with NVDA on Windows or VoiceOver on macOS.

### Checkpoint

- Demonstrate the main journey without a mouse, including error recovery.
- Show a correctly associated label, visible focus, and meaningful image alternative.
- Distinguish what the automatic audit checked from what you verified manually.

## Weekly project

Design a responsive page for a fictional local service such as a library, recycling point, or community workshop. Make the primary action usable without a mouse.

### Deliverables

- Responsive layouts at 360, 768, and 1280 CSS pixels without horizontal overflow.
- A complete keyboard path with visible focus and correctly associated form labels.
- A short design note explaining hierarchy, color, typography, and accessibility checks.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
