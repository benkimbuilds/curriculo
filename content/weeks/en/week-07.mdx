# Build with the Next.js App Router

Create a routed full-stack application, decide deliberately between server and client components, and validate forms on both sides of the network. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-07-lesson-01 -->
## Routes, layouts, and navigation

### Explanation

Begin the opportunity directory with a route map: collection, one record and a proposal form. A URL is a user-facing contract, not merely a folder name. In App Router, a folder adds a segment, page.tsx renders its screen and layout.tsx wraps descendants. Link preserves normal navigation behavior while enabling framework navigation.

Dynamic parameters in the current Next version are promises. Await them before reading the identifier. A missing record should render notFound(), not an empty success page. Loading and error boundaries describe actual waiting and failure states; neither replaces server validation. Read [pages and layouts](https://nextjs.org/docs/app/getting-started/layouts-and-pages) before extending the example.

### Example

```tsx
// app/opportunities/[id]/page.tsx
import { notFound } from "next/navigation";

const examples = [{ id: "community-garden", title: "Community garden" }];

export default async function Opportunity({
  params,
}: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const opportunity = examples.find(item => item.id === id);
  if (!opportunity) notFound();
  return <article><h1>{opportunity.title}</h1></article>;
}
```

### Guided exercise

1. Draw /opportunities, /opportunities/[id] and /opportunities/new with their intended read/write access.
2. Create list and detail pages using fictional data and Link; implement a shared section layout.
3. Add not-found.tsx and request an unknown ID; inspect the response and screen.
4. Navigate by keyboard, open a detail in a new tab, then use browser Back. Confirm URLs describe the selected record.

### Checkpoint

- Show the file corresponding to each of the three URLs and explain why a route group need not add a segment.
- Demonstrate a valid detail, a missing detail and browser Back without losing navigation context.

## Server and client boundaries

### Explanation

Keep reading, credentials and authorization on the server. Add a client boundary only for interactions that require state, events or browser APIs. Importing a database module into a Client Component risks exposing privileged logic and is blocked by server-only markers. A component being rendered by a server component does not make its props private: anything sent across the boundary is browser-visible.

The example keeps a fictional list in the page and passes only public titles to an interactive filter. Real records should be projected into an allowed public shape before passing them. Do not pass password hashes, session tokens or hidden moderation data and then hide them with CSS.

### Example

```tsx
// app/opportunities/filter.tsx
"use client";
import { useState } from "react";

export function Filter({ titles }: { titles: string[] }) {
  const [query, setQuery] = useState("");
  return (
    <section>
      <label htmlFor="query">Search / Buscar</label>
      <input id="query" value={query}
        onChange={event => setQuery(event.target.value)} />
      <ul>{titles.filter(title =>
        title.toLocaleLowerCase().includes(query.toLocaleLowerCase())
      ).map(title => <li key={title}>{title}</li>)}</ul>
    </section>
  );
}
// app/opportunities/page.tsx
import { Filter } from "./filter";
export default function Page() {
  return <Filter titles={["Community garden", "Library volunteers"]} />;
}
```

### Guided exercise

1. Implement the two files and verify typing updates the filter without making the page itself a Client Component.
2. Add a server module that returns records with public and private fields. Pass only public fields into Filter.
3. Inspect HTML and network payloads for a unique fictional private marker; it must not be present.
4. Explain how a large searchable dataset would move filtering to SQL and URL query parameters rather than downloading every record.

### Checkpoint

- Point to the specific browser interaction that justifies use client.
- Show a network response proving that your private fixture field never crossed the boundary.

## Forms and mutations

### Explanation

The browser's required attribute helps people, but callers can bypass it. Every mutation must validate FormData on the server and check permissions before writing. FormData fields may be strings, files or absent, so a type assertion is not validation. Extract only fields the operation accepts.

The following action is a validation exercise: it deliberately does not claim to persist a proposal. Use useActionState in a small Client Component to display its returned message and pending status. After adding the storage layer in week 8, save only parsed values, invalidate the list and redirect after success. Preventing double clicks improves UX; preventing duplicate writes requires a database constraint or idempotency rule.

### Example

```ts
// app/opportunities/actions.ts
"use server";

export async function validateProposal(
  _previous: { message: string },
  formData: FormData,
) {
  const value = formData.get("title");
  if (typeof value !== "string") return { message: "Title must be text / Usa texto" };
  const title = value.trim();
  if (title.length < 5 || title.length > 120) {
    return { message: "Use 5–120 characters / Usa 5–120 caracteres" };
  }
  return { message: "Valid, not saved yet / Válido, todavía no guardado" };
}
```

### Guided exercise

1. Create a labelled title form and wire the action through useActionState; render its message with aria-live and disable submit while pending.
2. Submit blank, short, valid and 121-character titles. Preserve the safe input so correction is easy.
3. Call the action through a real form while bypassing browser constraints; verify server checks still apply.
4. Write the future duplicate policy: which key identifies the same submission and what should a repeated request return?

### Checkpoint

- Demonstrate a server rejection despite bypassed browser validation.
- Explain the difference between a pending button and protection against duplicate database writes.
<!-- /lesson -->

## Rendering and caching

### Explanation

Rendering creates an interface; caching reuses prior work. They are related but distinct. A static public introduction may be built once, a public directory may accept a minute of staleness, and a private draft must be read with the current user's permissions. Never assume that server-side automatically means freshly queried, or that a page reload clears every cache.

This example requests a public API with a 60-second revalidation policy. OPPORTUNITIES_PUBLIC_API must point to a public JSON endpoint you control; its data must not contain personalized records. Next's Cache Components mode introduces additional conventions, so follow the documentation for your project's actual configuration rather than mixing tutorials.

### Example

```ts
// lib/public-directory.ts
import "server-only";

export async function readPublicDirectory() {
  const url = process.env.OPPORTUNITIES_PUBLIC_API;
  if (!url) throw new Error("Public API URL is missing");
  const response = await fetch(url, { next: { revalidate: 60 } });
  if (!response.ok) throw new Error("Directory request failed");
  return response.json();
}
```

### Guided exercise

1. Write a freshness table for public list, approved detail and private draft; define acceptable delay and owner.
2. Use a controlled public endpoint with a revision field. Read through the example and update the source revision.
3. Test navigation and a new request before/after the interval; record observed revisions. Revalidation may occur on a request and is not a timer guaranteeing immediate freshness.
4. Use request-time, uncached reads for private drafts and test two sessions. After an authorized edit, invalidate the affected public path using the appropriate Next API.

### Checkpoint

- Show observed old/new revisions and explain the stated freshness policy.
- Prove that one user's private draft is absent from another user's response, including cached navigation.
