# Persist and protect application data

Design a PostgreSQL model, evolve it with migrations, authenticate people safely, enforce ownership on the server, and deploy a recoverable application. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

<!-- lesson:week-08-lesson-01 -->
## Relational data modeling

### Explanation

Turn the tracker into entities and constraints before writing forms. A project belongs to one user; a task belongs to one project. Store the relationship once rather than repeating a user's email in every task. A primary key identifies a row; a foreign key preserves references. NOT NULL, UNIQUE and CHECK protect domain rules even when two requests arrive together.

The example uses fictional owner IDs to focus on modeling. In the complete application, reference the authentication library's actual user key rather than creating a competing identity table. Decide deletion behavior explicitly: RESTRICT rejects deleting occupied projects, while CASCADE would remove dependent tasks. Neither is universally correct.

### Example

```sql
CREATE TABLE projects (
  id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id TEXT NOT NULL,
  title TEXT NOT NULL CHECK (char_length(title) BETWEEN 1 AND 120),
  UNIQUE (owner_id, title)
);
CREATE TABLE tasks (
  id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  project_id INTEGER NOT NULL REFERENCES projects(id) ON DELETE RESTRICT,
  title TEXT NOT NULL,
  completed BOOLEAN NOT NULL DEFAULT false
);
CREATE INDEX tasks_project_idx ON tasks(project_id);
```

### Guided exercise

1. Draw users, projects and tasks with relationship cardinalities; choose deletion rules.
2. Apply the example only to a practice database and insert one project with two tasks.
3. Attempt duplicate project titles for one owner, a missing project reference and deletion of an occupied project; explain each result.
4. Adapt owner_id to your actual auth schema and add its foreign key through a migration. Document whether account deletion deletes or anonymizes owned data.

### Checkpoint

- Demonstrate three database-enforced invariants with failing SQL examples.
- Explain why uniqueness per owner differs from global title uniqueness.

## Queries and migrations

### Explanation

User input is data, never SQL source. Parameters separate those concerns, while ownership conditions ensure the selected rows belong to the session. Selecting by ID alone is not enough for a private tracker. Use a bounded result order and inspect query plans when real measurements reveal a problem.

Migrations are ordered changes committed with source. Test both an empty database and one containing existing rows. Adding a required column without a default can fail on populated data; an expand/backfill/contract sequence lets you preserve records. Reverting application code does not automatically reverse schema or data.

### Example

```ts
// In a server data module with a shared pg pool:
export async function renameProject(
  pool: import("pg").Pool,
  projectId: number,
  ownerId: string,
  title: string,
) {
  const { rows } = await pool.query(
    "UPDATE projects SET title = $1 WHERE id = $2 AND owner_id = $3 RETURNING id, title",
    [title, projectId, ownerId],
  );
  return rows[0] ?? null;
}
```

```sql
ALTER TABLE projects ADD COLUMN archived BOOLEAN NOT NULL DEFAULT false;
```

### Guided exercise

1. Create two fictional owners and projects. Call renameProject using the authenticated owner's ID, not a form-supplied value.
2. Try a quoted title and verify it remains data. Try another owner's project and confirm no row changes.
3. Save the archived-column migration, apply it to an empty database and an existing-data copy, and compare row counts.
4. Run EXPLAIN on a frequently used read query and decide whether an index matches its actual predicates.

### Checkpoint

- Show a quoted title saved safely and a cross-owner update returning no row.
- Demonstrate the same migration preserving existing rows and recreating the expected schema from scratch.

## Authentication and authorization

### Explanation

Use a maintained authentication library for credential hashing, sessions, verification and recovery. The complete library lesson provides Better Auth setup; finish that first. Do not replace it with a cookie containing a user ID. Authentication identifies a user; authorization checks that user's access to one operation and resource.

Every Server Action and Route Handler is a separate entry point. A protected layout or hidden button cannot secure a direct request. Derive owner identity from a validated session and constrain the database operation. Use a response that does not leak another user's private record when access is denied.

### Example

```ts
// Example Server Action after Better Auth and a shared pool are configured:
"use server";
import { headers } from "next/headers";
import { auth } from "@/lib/auth";
import { pool } from "@/lib/db";

export async function archiveProject(form: FormData) {
  const session = await auth.api.getSession({ headers: await headers() });
  if (!session?.user.emailVerified) return { error: "Verified session required" };
  const raw = form.get("projectId");
  if (typeof raw !== "string" || !/^[1-9]\d*$/.test(raw)) {
    return { error: "Invalid project" };
  }
  const id = Number(raw);
  if (!Number.isSafeInteger(id)) return { error: "Invalid project" };
  const { rowCount } = await pool.query(
    "UPDATE projects SET archived = true WHERE id = $1 AND owner_id = $2",
    [id, session.user.id],
  );
  return rowCount === 1 ? { ok: true } : { error: "Project unavailable" };
}
```

### Guided exercise

1. Configure the library's official Next integration and database migrations. Create two fictional accounts, verify them and sign in separately.
2. Implement the example using the constrained schema from this week. Confirm a user's own project can be archived.
3. Submit the second user's project ID while authenticated as the first. Confirm rejection and unchanged data.
4. Sign out, then retry the operation. Test an expired or reused recovery link through the provider flow and document the observed behavior.

### Checkpoint

- Demonstrate authenticated success, cross-owner denial and signed-out denial against the same action.
- Explain how password hashing, HttpOnly cookies and ownership filters solve different problems.

## Deployment and operations

### Explanation

A deploy is complete only when the running app can perform its real data flow. Compilation, process liveness and database readiness are separate signals. Keep secrets in provider configuration, run migrations before dependent code starts, and test sign-in, write and read at the public origin.

Use Railway web and PostgreSQL services or the lab's hosted environment. Personal paid hosting is not required for local completion. A managed database still needs a documented backup policy and a restore exercise. A backup that has never been restored is an assumption, not evidence.

### Example

```ts
// app/api/ready/route.ts
import { pool } from "@/lib/db";

export async function GET() {
  try {
    await pool.query("SELECT 1");
    return Response.json({ ready: true }, {
      headers: { "Cache-Control": "no-store" },
    });
  } catch {
    return Response.json({ ready: false }, {
      status: 503,
      headers: { "Cache-Control": "no-store" },
    });
  }
}
```

### Guided exercise

1. Run a production build locally, then start it with the same required environment names as hosting.
2. Deploy app and database, run migrations, configure HTTPS origin and verify /api/ready plus a real authenticated write/read.
3. Observe sanitized runtime logs while deliberately sending one invalid request. Record revision, migration and outcome without credentials.
4. Restore a backup into a separate disposable database and compare expected records. Document code rollback and whether the previous revision supports the current schema.

### Checkpoint

- Show a deployed revision and successful real write/read; a green build alone does not satisfy this check.
- Provide restore evidence and explain why readiness SELECT 1 does not prove that every required migration is present.
