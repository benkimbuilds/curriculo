# Persist and protect application data

Design a PostgreSQL model, evolve it with migrations, authenticate people safely, enforce ownership on the server, and deploy a recoverable application. This audit source assumes no prior programming experience and supports Windows and macOS. Complete the lessons in order: each one moves from explanation to a concrete example, guided practice, and observable evidence before the weekly project.

## Relational data modeling

### Explanation

Identify entities, stable identifiers, relationships, required fields, uniqueness, and deletion behavior. Normalize repeated facts and use constraints to protect invariants. The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. If reality differs, reduce the case until one cause is understandable. This habit replaces random trial and error with a repeatable way to learn and ask for help.

### Example

Read the example from top to bottom and point out the input, transformation, and result. Type it into a scratch file instead of pasting it; typing makes punctuation, names, and structure visible.

```sql
create table projects (
  id uuid primary key,
  owner_id uuid not null references users(id),
  title text not null check (length(title) between 1 and 120)
);
```

If you get stuck, return to the smallest example, read the first complete error, and change one thing. Ask for help with your prediction, the actual result, and what you tried—never with a password or token.

### Guided exercise

1. Create a disposable folder or file for this lesson and write one concrete prediction before running the example.
2. Type the example, run or inspect it with the appropriate tool, and compare the result with your prediction. Preserve the exact message if it fails.
3. Add tasks with a required project relationship and decide explicitly what deletion of a project should do.
4. Commit only when the change belongs in your project; for disposable practice, record the lesson in your learning notes instead.

### Checkpoint

- Draw an entity relationship diagram. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.
- Encode at least three domain rules as constraints. Show this with a run, capture, test, or explanation in your own words; repeating the sentence is not evidence.

The goal is not to memorize isolated syntax. You should be able to name the input, the decision made at each step, and the evidence that shows the result is correct. Predict before copying. if (project.ownerId !== session.userId) return forbidden();

## Weekly project

Build and deploy a tracker where verified users manage only their own projects and tasks. Include recovery-friendly errors and a simple account-data deletion path.

### Deliverables

- A constrained PostgreSQL schema and repeatable migrations tested from an empty database.
- Registration or sign-in, revocable sessions, and server-enforced ownership with negative tests.
- A Railway deployment guide covering environment values, health, migration, backup, and rollback checks.

Before submitting, open the project from a clean session, complete the primary journey, and connect each rubric criterion to concrete evidence. Never include passwords, tokens, precise locations, or real personal data.
