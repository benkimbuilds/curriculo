# Persiste y protege datos de la aplicación

Diseña un modelo PostgreSQL, evolúcionalo con migraciones, autentica con seguridad, aplica propiedad en servidor y despliega pensando en recuperación. Esta edición está escrita para quien empieza desde cero y puede trabajar en Windows o macOS. Completa las lecciones en orden: cada una incluye explicación, ejemplo, práctica y evidencia antes del proyecto semanal.

<!-- lesson:week-08-lesson-01 -->
## Modelado relacional de datos

### Explicación

Convierte el gestor en entidades y restricciones antes de crear formularios. Un proyecto pertenece a una persona y una tarea a un proyecto. Guarda la relación una vez en vez de repetir el correo en cada tarea. La clave primaria identifica; la foránea conserva referencias. NOT NULL, UNIQUE y CHECK protegen reglas incluso con solicitudes simultáneas.

El ejemplo usa IDs ficticios para estudiar el modelo. En la aplicación completa referencia la clave real de la biblioteca de autenticación, sin crear otra identidad. Define eliminación: RESTRICT impide borrar proyectos con tareas; CASCADE eliminaría dependencias. Ninguna opción es correcta para todos los productos.

### Ejemplo

```sql
CREATE TABLE projects (
  id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id TEXT NOT NULL,
  title TEXT NOT NULL CHECK (char_length(title) BETWEEN 1 AND 120),
  UNIQUE (owner_id, title)
);
CREATE TABLE tasks (
  id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  project_id INTEGER NOT NULL REFERENCES projects(id) ON DELETE RESTRICT,
  title TEXT NOT NULL,
  completed BOOLEAN NOT NULL DEFAULT false
);
CREATE INDEX tasks_project_idx ON tasks(project_id);
```

### Ejercicio guiado

1. Dibuja usuarios, proyectos y tareas con cardinalidades y reglas de eliminación.
2. Aplica el ejemplo solo a una base de práctica e inserta un proyecto con dos tareas.
3. Prueba título duplicado por propietario, referencia inexistente y eliminación de proyecto ocupado; explica resultados.
4. Adapta owner_id al esquema real de autenticación y agrega su clave foránea mediante migración. Documenta eliminación o anonimización al borrar una cuenta.

### Comprobación

- Demuestra tres reglas protegidas por la base con ejemplos SQL rechazados.
- Explica por qué unicidad por propietario difiere de unicidad global.

## Consultas y migraciones

### Explicación

La entrada del usuario es dato, nunca código SQL. Los parámetros separan ambas cosas y las condiciones de propietario limitan resultados a la sesión. Buscar solo por ID no basta para un gestor privado. Ordena resultados de forma estable y revisa planes cuando una medición revele problemas.

Las migraciones son cambios ordenados guardados con el código. Prueba desde una base vacía y otra con registros. Agregar una columna obligatoria sin valor puede fallar con datos existentes; ampliar, rellenar y finalmente restringir permite conservarlos. Revertir código no revierte automáticamente esquema ni datos.

### Ejemplo

```ts
// In a server data module with a shared pg pool:
export async function renameProject(
  pool: import("pg").Pool,
  projectId: number,
  ownerId: string,
  title: string,
) {
  const { rows } = await pool.query(
    "UPDATE projects SET title = $1 WHERE id = $2 AND owner_id = $3 RETURNING id, title",
    [title, projectId, ownerId],
  );
  return rows[0] ?? null;
}
```

```sql
ALTER TABLE projects ADD COLUMN archived BOOLEAN NOT NULL DEFAULT false;
```

### Ejercicio guiado

1. Crea dos propietarios ficticios. Llama renameProject con el ID autenticado, no el recibido en el formulario.
2. Prueba comillas en el título y confirma que siguen siendo datos. Intenta cambiar un proyecto ajeno: ninguna fila debe modificarse.
3. Guarda la migración archived, aplícala desde cero y sobre una copia con datos; compara cantidad de filas.
4. Ejecuta EXPLAIN sobre una lectura frecuente y decide si un índice corresponde a sus filtros reales.

### Comprobación

- Muestra un título con comillas guardado de forma segura y una actualización ajena sin resultados.
- Demuestra conservación de filas y creación del esquema desde cero con la misma migración.

## Autenticación y autorización

### Explicación

Usa una biblioteca mantenida para hashing, sesiones, verificación y recuperación. Completa primero la lección de biblioteca sobre Better Auth; no la sustituyas por una cookie que contenga un ID. Autenticación identifica; autorización comprueba acceso a una operación y recurso.

Cada Server Action y Route Handler es un punto de entrada. Un layout protegido o botón oculto no asegura solicitudes directas. Deriva propietario desde una sesión validada y limita la consulta. Ante denegación no reveles un registro privado ajeno.

### Ejemplo

```ts
// Example Server Action after Better Auth and a shared pool are configured:
"use server";
import { headers } from "next/headers";
import { auth } from "@/lib/auth";
import { pool } from "@/lib/db";

export async function archiveProject(form: FormData) {
  const session = await auth.api.getSession({ headers: await headers() });
  if (!session?.user.emailVerified) return { error: "Verified session required" };
  const raw = form.get("projectId");
  if (typeof raw !== "string" || !/^[1-9]\d*$/.test(raw)) {
    return { error: "Invalid project" };
  }
  const id = Number(raw);
  if (!Number.isSafeInteger(id)) return { error: "Invalid project" };
  const { rowCount } = await pool.query(
    "UPDATE projects SET archived = true WHERE id = $1 AND owner_id = $2",
    [id, session.user.id],
  );
  return rowCount === 1 ? { ok: true } : { error: "Project unavailable" };
}
```

### Ejercicio guiado

1. Configura integración Next y migraciones oficiales. Crea dos cuentas ficticias, verifícalas e inicia sesiones separadas.
2. Implementa el ejemplo con el esquema de esta semana y archiva un proyecto propio.
3. Envía el ID de la segunda cuenta desde la primera: comprueba rechazo y datos intactos.
4. Cierra sesión y repite. Prueba un enlace de recuperación vencido o reutilizado mediante el flujo del proveedor y documenta el resultado.

### Comprobación

- Demuestra éxito propio, rechazo por propietario ajeno y rechazo sin sesión en la misma acción.
- Explica qué problemas distintos resuelven hashing, cookies HttpOnly y filtros de propiedad.

## Despliegue y operación

### Explicación

Un despliegue termina cuando la aplicación ejecuta su recorrido real de datos. Compilación, proceso vivo y base lista son señales distintas. Guarda secretos en el proveedor, migra antes del código dependiente y prueba acceso, escritura y lectura en el origen público.

Usa servicios web y PostgreSQL de Railway o el alojamiento del laboratorio. No necesitas pagar alojamiento personal para completar localmente. Una base administrada también requiere política de respaldo y prueba de restauración; un respaldo nunca restaurado sigue siendo una suposición.

### Ejemplo

```ts
// app/api/ready/route.ts
import { pool } from "@/lib/db";

export async function GET() {
  try {
    await pool.query("SELECT 1");
    return Response.json({ ready: true }, {
      headers: { "Cache-Control": "no-store" },
    });
  } catch {
    return Response.json({ ready: false }, {
      status: 503,
      headers: { "Cache-Control": "no-store" },
    });
  }
}
```

### Ejercicio guiado

1. Compila producción localmente e inicia con los mismos nombres de variables requeridos en alojamiento.
2. Despliega aplicación y base, migra, configura origen HTTPS y comprueba /api/ready junto a escritura/lectura autenticadas.
3. Observa logs sanitizados durante una solicitud inválida. Registra revisión, migración y resultado sin credenciales.
4. Restaura un respaldo en una base descartable separada y compara registros. Documenta rollback de código y compatibilidad con el esquema actual.

### Comprobación

- Muestra revisión desplegada y escritura/lectura reales; una compilación verde no basta.
- Presenta evidencia de restauración y explica por qué SELECT 1 no demuestra todas las migraciones.

Construye y despliega un gestor donde personas verificadas administren sólo sus propios proyectos y tareas. Incluye errores recuperables y eliminación simple de datos.

- Esquema PostgreSQL con restricciones y migraciones repetibles probadas desde una base vacía.
