# Avanza a TypeScript y React

Usa tipos para volver visibles tus supuestos y compón interfaces React con componentes accesibles, estado predecible y flujo claro de datos. Esta edición está escrita para quien empieza desde cero y puede trabajar en Windows o macOS. Completa las lecciones en orden: cada una incluye explicación, ejemplo, práctica y evidencia antes del proyecto semanal.

<!-- lesson:week-06-lesson-01 -->
## TypeScript como documentación ejecutable

### Explicación

TypeScript comprueba supuestos antes de ejecutar JavaScript. Un tipo describe los valores esperados, pero no convierte una respuesta de red en un registro válido. Si el servidor envía un número donde esperabas un nombre, el navegador recibe ese número. Distinguir entre comprobación de compilación y validación durante ejecución es la habilidad central de esta lección.

Modela el directorio semanal con ID, nombre y categoría. Una unión como `"health" | "education"` expresa las alternativas permitidas mejor que `string`. Una función que recibe esa unión no acepta accidentalmente `"heath"` sin que el compilador avise. No uses `any` para silenciar esa información. Usa `unknown` cuando todavía no conoces la forma de un dato: necesitas acotarlo antes de leer sus propiedades o llamar métodos.

Acotar consiste en condiciones normales de JavaScript. Comprueba que el valor sea un objeto, descarta `null`, verifica las propiedades requeridas y revisa tipo y valores permitidos de cada una. Verificar solamente que existe un ID no demuestra que también haya nombre y categoría válidos. Un predicado de tipo es una promesa al compilador; si está incompleto puede fabricar confianza falsa.

Cuando la interfaz necesita explicar un fallo, devuelve un resultado de validación. Una unión discriminada permite comprobar un campo y acceder después al recurso validado o al mensaje de error. Así éxito y fallo son situaciones diferentes, en lugar de un objeto donde `resource` y `error` podrían faltar simultáneamente. Los tipos deben representar posibilidades reales del dominio, incluidos sus errores.

### Ejemplo

Guarda este ejemplo en un módulo TypeScript y ejecútalo con objetos válidos e inválidos. El recurso devuelto se construye con campos comprobados: propiedades adicionales de la entrada no pasan automáticamente a ser datos confiables.

```ts
type Resource = { id: string; name: string; category: "health" | "education" };
type ParseResult = { ok: true; resource: Resource } | { ok: false; error: string };
function parseResource(value: unknown): ParseResult {
  if (typeof value !== "object" || value === null) return { ok: false, error: "Se esperaba un objeto" };
  if (!("id" in value) || typeof value.id !== "string" || !value.id.trim()) return { ok: false, error: "Falta el ID" };
  if (!("name" in value) || typeof value.name !== "string" || !value.name.trim()) return { ok: false, error: "Falta el nombre" };
  if (!("category" in value) || (value.category !== "health" && value.category !== "education")) return { ok: false, error: "Categoría desconocida" };
  return { ok: true, resource: { id: value.id, name: value.name.trim(), category: value.category } };
}
const result = parseResource({ id: "r1", name: " Biblioteca ", category: "education" });
if (result.ok) console.log(result.resource.name);
else console.error(result.error);
```

El campo `ok` acota el resultado para quien llama la función. En la rama exitosa existe `resource`; en la otra existe `error`. Intenta acceder al recurso antes de comprobarlo y lee la objeción del compilador. No la resuelvas con `as Resource`: una aserción modifica lo que TypeScript cree sin validar el dato real. Del mismo modo, declara un campo opcional únicamente cuando la aplicación puede funcionar sin él.

Usa inferencia para valores locales evidentes y tipos explícitos en límites importantes: parámetros exportados, registros del dominio y props. Ejecuta la comprobación de tipos después de cada cambio, y luego ejecuta también el programa. Una compilación correcta no prueba la validación, una petición de red ni una interacción. Ambos tipos de evidencia son necesarios para localizar un defecto.

## Componentes y JSX

### Explicación

Un componente React describe una parte de la interfaz a partir de sus entradas. Comienza con un boceto: el directorio tiene encabezado, filtros, lista y formulario para agregar un borrador. Esas responsabilidades sugieren componentes útiles. Un límite debe facilitar reutilización o flujo de datos; crear un archivo para cada span no mejora automáticamente el diseño.

Las props transportan datos del padre al hijo. Un objeto tipado declara ese contrato: el padre entrega un recurso con categoría compatible y el hijo puede leerlo sin inventar valores predeterminados que oculten información faltante. Las props son entradas de solo lectura. Si un hijo necesita solicitar una acción, recibe un callback en vez de modificar directamente los datos del padre.

JSX es una extensión de JavaScript, no una cadena HTML. Requiere una expresión raíz, etiquetas cerradas explícitamente y propiedades como `className` o `htmlFor`. Usa fragmentos cuando agrupar hermanos no deba crear una caja de layout. Coloca valores dinámicos entre llaves y utiliza expresiones de JavaScript para derivarlos. Un objeto completo no es contenido visible útil; muestra sus campos.

Conserva HTML semántico dentro de los componentes. Una tarjeta puede ser un artículo con encabezado; una colección puede ser una lista. Su forma visual no determina que el contenedor deba ser un botón. Si un título navega, usa un enlace; si realiza una acción, un botón. Estas decisiones definen comportamiento de teclado y nombres accesibles antes de aplicar CSS.

### Ejemplo

La lista controla la iteración y la tarjeta controla la presentación. Ambas utilizan el mismo contrato de datos. La key corresponde al elemento devuelto directamente por `map`.

```tsx
type Resource = { id: string; name: string; category: "health" | "education" };
const categoryLabels = { health: "Salud", education: "Educación" };
export function ResourceCard({ resource }: { resource: Resource }) {
  return <article><h2>{resource.name}</h2><p>{categoryLabels[resource.category]}</p></article>;
}
export function ResourceList({ resources }: { resources: Resource[] }) {
  if (resources.length === 0) return <p>No hay recursos para estos filtros.</p>;
  return <ul>{resources.map(resource => <li key={resource.id}><ResourceCard resource={resource} /></li>)}</ul>;
}
```

Las keys identifican registros al insertar, eliminar y reordenar. Usar índices puede asociar el estado de una fila con otro registro. Generar una key aleatoria durante render comunica que cada fila es nueva. Genera IDs al crear registros y consérvalos con sus datos. La key es interna de React; si el hijo necesita un ID, debe recibirlo también como parte de sus props.

Renderiza primero dos recursos y después ninguno. El mensaje vacío es una situación intencional, no un diseño roto. Agrega un recurso sin cambiar la tarjeta: demuestra para qué sirven props e iteración. Luego cambia la etiqueta de categoría en un solo sitio y observa cómo todas las tarjetas usan la misma traducción. No confundas etiquetas visibles con identificadores estables que utiliza la lógica.

En Next.js una tarjeta puramente presentacional puede permanecer en servidor. Agregar estado o manejadores del navegador requiere una frontera cliente apropiada, no convertir toda la aplicación en código cliente. Esta lección se concentra en contratos; el módulo de rutas explica cómo componerlos con páginas y layouts. Observa también que extraer un componente no agrega una etiqueta HTML con ese nombre: React muestra los elementos que devuelve su función.

## Estado y eventos

### Explicación

El estado conserva información entre renderizados. En el directorio, el texto de búsqueda cambia al escribir y la colección cambia al agregar borradores. La lista filtrada se calcula a partir de esos hechos; no debe ser un tercer estado actualizado por separado. De otro modo, agregar un recurso o borrar un filtro podría dejar lista y conteo inconsistentes.

Un setter solicita otro render, pero no reemplaza la variable local del manejador en ejecución. Considera esa variable una instantánea: un log inmediatamente después del setter todavía ve el valor del render actual. Si el siguiente valor depende del anterior, usa un actualizador funcional para combinar correctamente varias actualizaciones pendientes. Los actualizadores deben ser puros; crea IDs antes de llamarlos y entrega esos valores a la actualización.

React controla un input mediante `value` y `onChange`. Inicializa texto con una cadena vacía y actualízalo desde el evento. Un input controlado sin manejador queda esencialmente de solo lectura. Cuando varios componentes necesitan el mismo valor, mueve su propiedad al ancestro común más cercano que resulte útil y pasa datos y callbacks hacia abajo. No sincronices copias de hermanos con efectos.

Objetos y arreglos de estado son instantáneas inmutables. Crea otro arreglo al agregar o quitar registros y copia cada registro que cambie. Un spread solo copia un nivel. Así los renders anteriores conservan significado y la comparación de identidad detecta el cambio. Modificar con `push` y devolver el mismo arreglo puede dejar la interfaz desactualizada.

### Ejemplo

Este componente deriva resultados y conteo de un solo estado de búsqueda. Trata la ausencia de coincidencias como una situación normal de la interfaz.

```tsx
"use client";
import { useState } from "react";
type Resource = { id: string; name: string };
export function Directory({ initialResources }: { initialResources: Resource[] }) {
  const [resources, setResources] = useState(initialResources);
  const [query, setQuery] = useState("");
  const visible = resources.filter(item => item.name.toLocaleLowerCase().includes(query.trim().toLocaleLowerCase()));
  function addDraft() {
    const draft = { id: crypto.randomUUID(), name: "Biblioteca comunitaria" };
    setResources(previous => [...previous, draft]);
  }
  return <section>
    <label>Buscar<input value={query} onChange={event => setQuery(event.target.value)} /></label>
    <p>{visible.length} resultados</p>
    <button onClick={addDraft}>Agregar borrador de ejemplo</button>
    {visible.length === 0 ? <p>No hay coincidencias.</p> : <ul>{visible.map(item => <li key={item.id}>{item.name}</li>)}</ul>}
  </section>;
}
```

Sigue una pulsación: el navegador produce un cambio, el manejador lee su valor, el setter programa render, el filtro usa la consulta nueva y React confirma lista y conteo. No necesitas un efecto porque no estás sincronizando nada externo. Agregar un borrador sigue el mismo recorrido con un arreglo nuevo. Si no coincide con la búsqueda actual, permanece oculto correctamente hasta cambiar el filtro.

La inicialización se utiliza cuando se monta la instancia. Cambiar después `initialResources` no reemplaza automáticamente el estado local. Decide si el componente posee una copia editable o debe mostrar directamente props entrantes; mezclar ambos modelos silenciosamente genera reinicios sorpresivos. Este ejemplo posee una colección local y no la conserva después de recargar.

Al introducir el formulario real, separa su texto provisional de un recurso validado. Un envío inválido debe mostrar un error y preservar el borrador para corregirlo. Un envío correcto agrega exactamente un registro y limpia los campos correspondientes. Esas transiciones observables serán la base de las pruebas de la siguiente lección. Antes de escribirlas, comprueba a mano qué sucede cuando agregas algo que no coincide con el filtro activo.

## Pruebas de componentes

### Explicación

Una prueba útil describe algo que una persona puede lograr: buscar un recurso, agregar un borrador válido o recuperarse de datos incorrectos. Debe seguir pasando al renombrar variables internas o dividir componentes sin cambiar comportamiento. Inspeccionar estado privado vuelve difícil refactorizar y puede omitir controles que no funcionan.

React Testing Library renderiza componentes en un DOM de prueba. Vitest ejecuta y verifica; jsdom simula el DOM; jest-dom agrega afirmaciones legibles; user-event simula secuencias de interacción. No es un navegador visual: no garantiza espaciado correcto ni toda la navegación. Revisa layout y recorridos completos con un navegador real.

Consulta por rol y nombre accesible cuando sea posible. Un input se encuentra por su etiqueta y un botón por su propósito visible. Así una etiqueta faltante provoca un fallo útil, en lugar de ignorarse mediante un selector CSS. `getBy` espera un elemento ahora, `queryBy` permite comprobar ausencia y `findBy` espera su aparición asíncrona. Elige según comportamiento, no para ocultar una prueba inestable.

Cada prueba prepara datos y componente, actúa mediante una interacción y comprueba el resultado. Crea `userEvent.setup()` dentro de la prueba antes de renderizar, y espera sus acciones con `await`. Asegura limpieza de RTL después de cada prueba. Si el ejecutor no expone hooks globales para limpieza automática, registra explícitamente `afterEach(cleanup)` en setup.

### Ejemplo

El ejemplo utiliza Directory de la lección anterior. Sus datos hacen significativa tanto la afirmación positiva como la negativa: la biblioteca existe antes de filtrar y desaparece después.

```tsx
import { it, expect } from "vitest";
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { Directory } from "./Directory";

it("filtra recursos y los restaura al borrar", async () => {
  const user = userEvent.setup();
  render(<Directory initialResources={[
    { id: "clinic", name: "Clínica comunitaria" },
    { id: "library", name: "Biblioteca" },
  ]} />);
  const search = screen.getByRole("textbox", { name: "Buscar" });
  await user.type(search, "CLÍNICA");
  expect(screen.getByText("Clínica comunitaria")).toBeVisible();
  expect(screen.queryByText("Biblioteca")).not.toBeInTheDocument();
  expect(screen.getByText("1 resultados")).toBeVisible();
  await user.clear(search);
  expect(screen.getByText("Biblioteca")).toBeVisible();
});
```

La prueba revisa mayúsculas y recuperación, no solamente que exista un input. Si lo reemplazas por un campo que no hace nada, falla. Si renombras `query`, sigue pasando. Esa es la diferencia entre un contrato de comportamiento y un espejo de la implementación.

Para el formulario de alta, envía espacios y comprueba que aparece un error legible, no se agrega un recurso y el borrador permanece disponible. Corrige el valor y envía exitosamente. No hagas una petición real salvo que estés verificando intencionalmente esa integración; simula la respuesta externa en su límite cuando corresponda. Un callback simulado comprueba lo que solicitó el componente, pero no demuestra que el servidor real persista un registro.

Los snapshots comparan marcado serializado con una versión guardada. Pueden ser útiles para una salida pequeña y estable, pero no ejercitan clics ni validan reglas. Actualizarlos sin revisar puede aprobar una regresión. Conserva mensajes específicos que expliquen la tarea rota y lee el DOM renderizado cuando falle una consulta antes de debilitar la afirmación. Si la interfaz cambia de una lista a otra estructura semántica válida, evalúa el contrato observable antes de concluir que todo fallo indica un defecto del producto.

4. Ejecuta la suite y revisa el mismo recorrido manualmente a un ancho pequeño. Registra qué demuestra cada verificación.

- Muestra una búsqueda con recuperación que pasa, y demuestra que un filtro roto deliberadamente hace fallar su prueba.
- Muestra una validación que preserva datos escritos y explica por qué un snapshot solo no demuestra ese comportamiento.

## Proyecto semanal

Crea una app React tipada para explorar y filtrar recursos comunitarios ficticios. Se puede agregar un borrador local sin usar datos reales de contacto.

### Entregables

- Modelos tipados de recurso, categoría y formulario con validación en el límite de entrada.
- Componentes semánticos reutilizables con flujos de filtro, alta, vacío y validación.
- Pruebas de un flujo exitoso y uno inválido, más un README centrado en decisiones.

Antes de entregar, abre el proyecto desde una sesión limpia, recorre el flujo principal y compara cada criterio de la rúbrica con evidencia concreta. No incluyas contraseñas, tokens, ubicaciones precisas ni datos personales reales.
