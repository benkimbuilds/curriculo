# Construye con Next.js App Router

Crea una aplicación full stack con rutas, decide conscientemente entre componentes de servidor y cliente, y valida formularios a ambos lados de la red. Esta edición está escrita para quien empieza desde cero y puede trabajar en Windows o macOS. Completa las lecciones en orden: cada una incluye explicación, ejemplo, práctica y evidencia antes del proyecto semanal.

<!-- lesson:week-07-lesson-01 -->
## Rutas, layouts y navegación

### Explicación

Comienza el directorio de oportunidades con un mapa: colección, detalle y formulario de propuesta. Una URL es un contrato con quien utiliza el sitio. En App Router, una carpeta agrega un segmento, page.tsx renderiza su pantalla y layout.tsx envuelve a sus descendientes. Link conserva navegación normal y permite navegación del framework.

Los parámetros dinámicos de Next actual son promesas: espéralos antes de leer el identificador. Un registro ausente debe producir notFound(), no una página vacía exitosa. Loading y error describen espera y fallas reales; ninguno reemplaza validación del servidor. Lee [páginas y layouts](https://nextjs.org/docs/app/getting-started/layouts-and-pages) antes de ampliar el ejemplo.

### Ejemplo

```tsx
// app/opportunities/[id]/page.tsx
import { notFound } from "next/navigation";

const examples = [{ id: "community-garden", title: "Community garden" }];

export default async function Opportunity({
  params,
}: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const opportunity = examples.find(item => item.id === id);
  if (!opportunity) notFound();
  return <article><h1>{opportunity.title}</h1></article>;
}
```

### Ejercicio guiado

1. Dibuja /opportunities, /opportunities/[id] y /opportunities/new con sus permisos de lectura/escritura.
2. Crea lista y detalle con datos ficticios y Link; implementa un layout compartido.
3. Agrega not-found.tsx y solicita un ID desconocido; inspecciona respuesta y pantalla.
4. Navega con teclado, abre detalle en otra pestaña y usa Atrás. Confirma que la URL identifica el registro.

### Comprobación

- Muestra el archivo correspondiente a cada URL y explica por qué un grupo de rutas no necesita agregar un segmento.
- Demuestra un detalle válido, uno ausente y el botón Atrás sin perder el contexto.

## Fronteras entre servidor y cliente

### Explicación

Mantén lectura, credenciales y autorización en el servidor. Agrega una frontera cliente solo para estado, eventos o APIs del navegador. Importar la base en un Client Component mezcla responsabilidades; los marcadores server-only ayudan a detectarlo. Las props que cruzan esa frontera son visibles en el navegador aunque el padre se haya ejecutado en el servidor.

El ejemplo conserva una lista ficticia en la página y pasa únicamente títulos públicos al filtro interactivo. Con datos reales crea una proyección permitida antes de pasarla. No envíes hashes, tokens o datos privados para luego ocultarlos mediante CSS.

### Ejemplo

```tsx
// app/opportunities/filter.tsx
"use client";
import { useState } from "react";

export function Filter({ titles }: { titles: string[] }) {
  const [query, setQuery] = useState("");
  return (
    <section>
      <label htmlFor="query">Search / Buscar</label>
      <input id="query" value={query}
        onChange={event => setQuery(event.target.value)} />
      <ul>{titles.filter(title =>
        title.toLocaleLowerCase().includes(query.toLocaleLowerCase())
      ).map(title => <li key={title}>{title}</li>)}</ul>
    </section>
  );
}
// app/opportunities/page.tsx
import { Filter } from "./filter";
export default function Page() {
  return <Filter titles={["Community garden", "Library volunteers"]} />;
}
```

### Ejercicio guiado

1. Implementa ambos archivos y comprueba el filtro sin convertir toda la página en Client Component.
2. Agrega un módulo del servidor con campos públicos y privados. Pasa solo campos públicos a Filter.
3. Busca una marca privada ficticia en HTML y respuestas de red: no debe aparecer.
4. Explica cómo una colección grande trasladaría la búsqueda a SQL y parámetros de URL en vez de descargar todo.

### Comprobación

- Señala la interacción concreta que justifica use client.
- Muestra una respuesta de red que pruebe que el campo privado no cruzó la frontera.

## Formularios y mutaciones

### Explicación

El atributo required ayuda, pero cualquier cliente puede omitirlo. Cada mutación valida FormData en el servidor y comprueba permisos antes de escribir. Los campos pueden ser cadenas, archivos o estar ausentes: una aserción TypeScript no valida. Extrae solo los campos aceptados.

La acción siguiente es un ejercicio de validación y no afirma guardar la propuesta. Usa useActionState en un Client Component pequeño para mostrar mensaje y estado pendiente. Al agregar persistencia en semana 8, guarda solo valores validados, invalida la lista y redirige tras éxito. Desactivar un botón mejora UX; impedir escrituras duplicadas requiere una restricción o regla de idempotencia.

### Ejemplo

```ts
// app/opportunities/actions.ts
"use server";

export async function validateProposal(
  _previous: { message: string },
  formData: FormData,
) {
  const value = formData.get("title");
  if (typeof value !== "string") return { message: "Title must be text / Usa texto" };
  const title = value.trim();
  if (title.length < 5 || title.length > 120) {
    return { message: "Use 5–120 characters / Usa 5–120 caracteres" };
  }
  return { message: "Valid, not saved yet / Válido, todavía no guardado" };
}
```

### Ejercicio guiado

1. Crea un formulario etiquetado y conecta la acción mediante useActionState; muestra el mensaje con aria-live y desactiva envío pendiente.
2. Envía títulos vacío, corto, válido y de 121 caracteres. Conserva el valor seguro para corregirlo.
3. Prueba omitiendo restricciones del navegador y confirma que el servidor mantiene las reglas.
4. Escribe la política futura de duplicados: qué clave identifica el mismo envío y qué responde una repetición.

### Comprobación

- Demuestra rechazo del servidor aunque se omita validación del navegador.
- Explica la diferencia entre botón pendiente y protección contra escrituras duplicadas.

## Renderizado y caché

### Explicación

Renderizar produce una interfaz; cachear reutiliza trabajo anterior. Una introducción pública puede preconstruirse, un directorio público puede tolerar un minuto de desfase y un borrador privado requiere permisos de la sesión actual. Ejecutar en el servidor no significa automáticamente consultar datos frescos; recargar tampoco elimina todas las cachés.

El ejemplo consulta una API pública con revalidación de 60 segundos. OPPORTUNITIES_PUBLIC_API debe apuntar a un endpoint JSON público que controles, sin información personalizada. El modo Cache Components agrega otras convenciones: sigue la documentación correspondiente a la configuración real del proyecto.

### Ejemplo

```ts
// lib/public-directory.ts
import "server-only";

export async function readPublicDirectory() {
  const url = process.env.OPPORTUNITIES_PUBLIC_API;
  if (!url) throw new Error("Public API URL is missing");
  const response = await fetch(url, { next: { revalidate: 60 } });
  if (!response.ok) throw new Error("Directory request failed");
  return response.json();
}
```

### Ejercicio guiado

1. Escribe reglas de frescura para lista pública, detalle aprobado y borrador privado.
2. Usa un endpoint público controlado con campo de revisión; consúltalo y actualiza la revisión de origen.
3. Prueba navegación y solicitudes antes/después del intervalo. La revalidación puede ocurrir al recibir una solicitud; no es un temporizador que garantice actualización inmediata.
4. Mantén borradores en lecturas privadas sin caché compartida y prueba dos sesiones. Tras edición autorizada invalida la ruta pública afectada con la API de Next correspondiente.

### Comprobación

- Muestra revisiones observadas y explica la política de frescura.
- Prueba que un borrador privado no aparece en la respuesta de otra cuenta, incluida navegación cacheada.
