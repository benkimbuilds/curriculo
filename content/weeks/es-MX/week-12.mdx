# Fortalece, lanza y presenta tu proyecto final

Termina el alcance más valioso, prueba y observa producción, mejora tu historia de portafolio y practica una entrevista técnica y demo breves. Esta edición está escrita para quien empieza desde cero y puede trabajar en Windows o macOS. Completa las lecciones en orden: cada una incluye explicación, ejemplo, práctica y evidencia antes del proyecto semanal.

<!-- lesson:week-12-lesson-01 -->
## Pase de calidad y seguridad

### Explicación

Una revisión de calidad empieza por las promesas de aceptación. Comprueba primero reglas cuyo fallo perdería trabajo, expondría datos o engañaría a alguien. Para préstamos: disponibilidad, propiedad, persistencia y recuperación. Una captura no demuestra esas propiedades.

Usa niveles distintos para preguntas distintas. Una prueba unitaria comprueba una regla pequeña sin navegador ni base. Una de integración comprueba límites reales, como una restricción de datos u operación autenticada. Una de navegador verifica recorrido, etiquetas, foco y resultado visible. Repetir lo mismo en todos los niveles aporta poco: ubica cada prueba donde se pueda entender su fallo.

Autorizar requiere probar al menos dos cuentas. A puede acceder a su registro y B no, incluso cambiando URL o cuerpo de solicitud directamente. Ocultar enlaces no basta. Prueba sesión vencida, ids mal escritos, registros ausentes y envíos repetidos. Usa datos ficticios y entornos desechables.

Inspecciona teclado, pantalla estrecha, texto ampliado y red lenta. Las etiquetas deben explicar controles, los errores señalar recuperación y el foco permanecer útil. Medir desbordamiento no detecta texto pegado a divisores ni jerarquía ilegible: revisa también las pantallas reales.

### Ejemplo

Esta prueba de Node expresa una regla de dominio pequeña. Mantén aparte la integración del invariante de un préstamo activo: dos solicitudes concurrentes pueden pasar esta función antes de insertar.

~~~js
import test from "node:test";
import assert from "node:assert/strict";

function canBorrow({ active, disabled }) {
  return !active && !disabled;
}
test("solo se presta equipo disponible y habilitado", () => {
  assert.equal(canBorrow({ active: false, disabled: false }), true);
  assert.equal(canBorrow({ active: true, disabled: false }), false);
  assert.equal(canBorrow({ active: false, disabled: true }), false);
  assert.equal(canBorrow({ active: true, disabled: true }), false);
});
~~~

La tabla cubre combinaciones. No sustituye validación: rechaza campos ausentes o tipos incorrectos en el límite, en vez de confiar en valores verdaderos o falsos por conversión. Tampoco demuestra propiedad en el servidor; eso necesita pruebas contra la operación real.

### Ejercicio guiado

1. Relaciona cada criterio con una comprobación automatizada o manual útil. Identifica lagunas antes de agregar más.
2. Ejecuta reglas y rompe una temporalmente para comprobar que su prueba detecta el error.
3. Prueba lectura y escritura propia/ajena mediante el servidor, no solo la pantalla.
4. Inspecciona las páginas del recorrido en teléfono y escritorio, con teclado y red lenta.
5. Revisa historial, registros, formularios y configuración buscando secretos y recolección innecesaria. Elimina campos no usados y documenta pendientes.

### Comprobación

- El informe conecta cada promesa importante con evidencia o un defecto explícito.
- Otra cuenta no puede leer ni modificar registros privados alterando solicitudes.
- El recorrido permanece legible y recuperable en pantalla estrecha, con teclado y al fallar la red.

## Preparación para producción

### Explicación

Estar listo para producción significa que el sistema desplegado inicia, usa dependencias reales y se recupera de fallos esperados. Compilar no demuestra conexión a base, entrega de correo, ejecución de worker ni recorrido completo.

Separa vida y preparación. Una comprobación de vida indica que el proceso responde; una de preparación verifica dependencias necesarias. En esta plataforma /api/health y /api/ready cumplen funciones diferentes. El worker necesita evidencia propia: proceso activo y trabajo ficticio completado o comprobación apropiada de cola, no solo que cargue la web.

La configuración pertenece al entorno que la usa. URL de base, secretos de autenticación y credenciales de correo quedan en el servidor. Origen público y orígenes confiables deben coincidir con el sitio HTTPS real. Un correo capturado por una bandeja local no demuestra entrega en producción. Si tu proyecto los incluye, verifica registro, confirmación y recuperación con cuentas de prueba autorizadas.

Las migraciones cambian datos persistentes y requieren recuperación. Prefiere cambios compatibles con versiones vieja y nueva durante despliegues progresivos. Respalda antes de cambios riesgosos y practica restaurar en otra base. Ver un respaldo en un panel es evidencia más débil que haber probado una restauración.

Volver a una versión anterior no revierte automáticamente esquema ni datos perdidos. Registra versión previa, pasos y condiciones para regresar. Evita editar migraciones destructivamente para que una aplicación vieja arranque.

### Ejemplo

Este repositorio dispone de estos comandos para una lista de publicación. Ejecuta operaciones de base solo contra el entorno previsto y verifica su identidad antes.

~~~sh
pnpm lint
pnpm typecheck
pnpm test
pnpm content:validate
pnpm build
~~~

Después de publicar, sustituye el origen de ejemplo por tu sitio real:

~~~sh
curl --fail --silent --show-error https://your-app.example/api/health
curl --fail --silent --show-error https://your-app.example/api/ready
~~~

Una respuesta 200 es solo una comprobación. Confirma commit desplegado, revisa registros seguros de inicio/migración y realiza un recorrido ficticio que escriba y lea datos. Si hay correo y worker, verifícalos explícitamente. No incluyas credenciales en capturas ni informes.

### Ejercicio guiado

1. Lista variables requeridas y servicio responsable sin sus valores secretos.
2. Aplica migraciones en una base desechable nueva e inicia con instrucciones documentadas.
3. Publica, comprueba salud/preparación y prueba el recorrido desde una cuenta limpia.
4. Crea y restaura un respaldo de prueba en otra base desechable. Compara conteos y restricciones esperados.
5. Ensaya regresar a una versión compatible anterior. Anota qué requiere una decisión independiente sobre datos.

### Comprobación

- El informe distingue compilación, proceso vivo, base utilizable, correo y worker.
- Registra versión desplegada y recorrido ficticio exitoso.
- Respaldo y reversión son reproducibles sin asumir que volver código revierte datos.

## Portafolio y documentación

### Explicación

Quien revisa un portafolio puede tener pocos minutos. Ayúdale a entender problema, contribución y evidencia. Una lista de logos dice poco de tus decisiones. Explica por qué elegiste un diseño, qué alternativas consideraste y qué limitación permanece.

Escribe el README para quien nunca vio el proyecto. Empieza por problema y resultado principal, con captura o demostración. Indica si es aprendizaje, adaptación o trabajo usado por personas reales. No inventes usuarios ni atribuyas solo a ti una función de equipo.

Separa evaluación rápida e instalación. Una persona no técnica necesita descripción y demostración; una técnica, prerrequisitos, comandos exactos, nombres de variables, migraciones, datos de prueba y pruebas. Usa valores ficticios para secretos y explica cómo obtener configuración local. Mantén instrucciones sincronizadas con scripts reales.

La documentación debe mostrar límites. Si la IA es una simulación determinista, dilo. Si el correo requiere configuración, adviértelo antes de que prueben recuperación. Si evaluación automática cubre solo algunos criterios, distínguela de revisión humana. La precisión permite valorar el trabajo justamente.

### Ejemplo

Completa este esquema con hechos del proyecto:

~~~markdown
# Préstamo de equipo
Aplicación pequeña para consultar disponibilidad y registrar préstamos.

## Demostración
URL, captura e instrucciones seguras para probar con datos ficticios.

## Mi contribución
Rutas, reglas, pruebas y responsabilidades de colaboración.

## Arquitectura
Navegador -> operación autenticada -> restricciones PostgreSQL.

## Ejecución local
Versión de runtime, instalación, plantilla de variables,
migraciones, datos ficticios e inicio.

## Verificación
Comandos de pruebas y recorrido manual principal.

## Decisiones y límites
Por qué la base impone un préstamo activo.
Qué está fuera de alcance y qué falta verificar.

## Créditos
Currículo, bibliotecas, adaptaciones y licencias aplicables.
~~~

En un caso de estudio, profundiza en una decisión: dos personas enviaban a la vez; se necesitó una restricción de base; la segunda recibe conflicto recuperable. Incluye prueba o recorrido. Eso explica más que “backend robusto”.

### Ejercicio guiado

1. Elige dos o tres proyectos que muestren habilidades distintas. Quita enlaces rotos y ejemplos redundantes.
2. Escribe problema, restricciones, contribución, decisión, evidencia y próxima mejora.
3. Sigue el README desde un clon limpio sin instrucciones adicionales. Corrige cada paso ausente.
4. Pide a alguien no técnico que explique el proyecto después de un minuto y a alguien técnico que ejecute una prueba.
5. Revisa capturas, cuentas ficticias e historial por información privada. Atribuye adaptaciones y colaboraciones.

### Comprobación

- Quien revisa identifica rápidamente problema y contribución personal.
- Instalación y verificación funcionan sin pasos manuales ocultos.
- Afirmaciones sobre IA, publicación, uso y evaluación coinciden con evidencia.

## Demo y entrevista

### Explicación

Una demostración es una explicación breve respaldada por un recorrido confiable. Elige un problema y muestra su resolución. Tres minutos no requieren visitar todas las páginas; demasiadas funciones dificultan entender comportamiento principal y decisiones.

Prepara el estado inicial: datos ficticios, cuenta de prueba y equipo disponible. Verifica la versión desplegada. Ten capturas o grabación breve por si falla la red, identificadas como evidencia grabada y no como ejecución en vivo.

Usa contexto, acción, resultado y una decisión técnica. En préstamos, explica los viajes en vano, muestra disponibilidad y salida, y después el préstamo persistido al recargar. Describe brevemente cómo la base impide duplicados simultáneos. Termina con una limitación y próxima mejora a comprobar.

En entrevistas, conecta afirmaciones con evidencia mediante situación, acción y resultado. Distingue tu contribución de la del equipo. Un intento fallido puede explicar aprendizaje, pero dedica más tiempo al razonamiento final y su prueba.

### Ejemplo

Un guion de tres minutos:

~~~text
0:00–0:30  Quién pide equipo y qué fallaba antes.
0:30–1:20  Entrar con cuenta de prueba, elegir equipo y pedirlo.
1:20–1:45  Recargar y mostrar préstamo persistido.
1:45–2:20  Explicar prueba concurrente y restricción de préstamo activo.
2:20–2:45  Mostrar recuperación ante fallo y una limitación.
2:45–3:00  Plantear siguiente experimento y abrir preguntas.
~~~

Para un ejercicio técnico, reformula entradas y salidas, pregunta restricciones y recorre un ejemplo pequeño. Una solución sencilla correcta es buen inicio; explica complejidad y mejoras después. Si no recuerdas un método, di qué consultarías en documentación en vez de inventarlo.

Prepárate para “¿qué pasa con dos solicitudes simultáneas?”, “¿cómo impides que otra cuenta lea esto?” y “¿qué no cubre la prueba?”. Responde con código y evidencia reales. Reconocer un límite y un plan es mejor que afirmar confiabilidad absoluta.

### Ejercicio guiado

1. Escribe y ensaya un guion de tres minutos con un recorrido completo real.
2. Ejecútalo dos veces desde el estado documentado, incluida una sesión nueva.
3. Practica un fallo de red y pasa a capturas identificadas sin perder la explicación.
4. Responde cinco preguntas técnicas y resuelve un problema pequeño con un colega. Piensa en voz alta, aclara, prueba y resume.
5. Registra comentarios sobre claridad, tiempo, afirmaciones sin sustento y dudas. Revisa y ensaya otra vez.

### Comprobación

- La demostración cabe en tres minutos y prueba persistencia y regla principal.
- Existe alternativa identificada honestamente si hace falta.
- Explicas una decisión entre alternativas, un defecto reparado y una limitación con evidencia.

## Proyecto semanal

Publica el recorrido principal en una URL HTTPS estable, preséntalo y crea un caso de estudio. El equipo es opcional, pero cada aportación debe ser explícita.

### Entregables

- Release con flujo principal, autorización, validación, revisiones responsivas y de teclado, monitoreo y rollback.
- Repositorio reproducible con pruebas, arquitectura, divulgaciones de privacidad e IA, commit desplegado y registro de aportación.
- Caso de estudio conciso, demo de tres minutos, bitácora de comentarios, retrospectiva y próximos pasos con evidencia.

Antes de entregar, abre el proyecto desde una sesión limpia, recorre el flujo principal y compara cada criterio de la rúbrica con evidencia concreta. No incluyas contraseñas, tokens, ubicaciones precisas ni datos personales reales.
